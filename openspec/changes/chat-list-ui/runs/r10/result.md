# Результат — tester / cover (r10, возврат по feedback)

## Что сделано

Планировщик (r9) провёл решение владельца «порядок задаёт сервер» по `proposal.md`, дельтам `specs/`,

### `coverage.yaml`

Переписан под обе дельты: 15 утверждений, имена capability, требований и сценариев — дословно из дельт.

- Новая capability в покрытии: `plugins/telegram-chat-list/http-api`, требование «Список сохранённых чатов»
  (секция MODIFIED) — сценарии «Запрос списка чатов», «Порядок записей в ответе», «Отсутствующие значения полей».
- `plugins/telegram-chat-list/web-ui`: сценарий «Список отсортирован по убыванию даты» удалён (его больше нет
  в дельте), вместо него — «Список выводится в порядке ответа API» и «Изменить порядок вывода нельзя»;
  остальные 10 сценариев сохранены. Формулировка причины для требования «Порядок вывода чатов» приведена
  к новому смыслу: раздел ничего не сортирует, проверяется совпадение порядка строк с порядком ответа API.
- Все 15 утверждений — `manual` с причиной. Для `web-ui` причина прежняя (нет тест-раннера для `frontend/**`,
  нет браузерных и e2e-тестов — `testing.md`). Для `http-api` причина новая и обоснована по коду:
  уровень «component (C#, плагин с зависимостями)» в `testing.md` помечен «—»; unit неприменим, потому что
  `GetChatList` — приватный обработчик, данные берёт у `DatabasePlugin.OpenSession()`
  (`ThinkingHome.Plugins.Database/DatabasePlugin.cs:56-59`), а `DatabasePlugin` — обычный класс
  с невиртуальным `OpenSession()` (Moq подменить не может) и требует строку подключения Npgsql
  (`DatabasePlugin.cs:21-26`). Проверить порядок «в памяти», не переписав `OrderByDescending` в самом тесте
  (запрещено правилом роли: не дублировать продуктовую логику), нельзя — поэтому оракул — ответ работающего API.

### `test-plan.md`

15 ручных проверок, по одной на утверждение, разбиты на два раздела.

- Новый раздел «HTTP API списка чатов» (проверки 1–3): состав ответа, порядок по убыванию `date`
  (`curl -s 'http://localhost:8080/api/telegram-chat-list/web-api/list'`, ожидаемая последовательность
  `alpha` → `bravo` → `chatId = 1004` → `charlie`), `null` в `login`, `firstName`, `lastName`.
  Порядок теперь наблюдаем без браузера, одним запросом.
- Раздел веб-интерфейса (проверки 4–15): прежняя проверка 4 «Список отсортирован по убыванию даты»
  заменена двумя — «Список выводится в порядке ответа API» (главный оракул: последовательность записей
  в теле ответа и последовательность строк таблицы совпадают элемент в элемент; ожидаемое убывание `date` —
  дополнительное наблюдение) и «Изменить порядок вывода нельзя» (клик по заголовкам колонок порядок не меняет,
  переключателей сортировки нет). Остальные проверки перенумерованы без изменения содержания.
- В «Общее окружение» добавлен ожидаемый порядок набора данных A по убыванию даты и оговорка про равные даты;
  в чеклист перед мержем — отдельные пункты про проверки 1–3 и 4–15.
- Четыре неблокирующих замечания ревьюера (`evidence/tests-review-1.md`), выполненные в r8, сохранены:
  консоль браузера вместо лога приложения (проверка 12), статический шаг про состав `ProjectReference`
  (проверка 4), прогон при `culture: en-US` (проверка 14), оракул порядка не зависит от неуправляемого
  порядка выдачи PostgreSQL (проверки 2 и 7 — теперь порядок задан контрактом API, а не случаен).
