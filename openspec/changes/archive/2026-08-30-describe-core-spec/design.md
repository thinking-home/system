## Context

`openspec/specs` пока пуст. Ядро (`ThinkingHome.Core.Infrastructure`, `ThinkingHome.Core.Plugins`) — небольшая, стабильная часть кода (жизненный цикл приложения/плагинов, безопасный вызов обработчиков, вспомогательные реестры), от которой зависят все плагины. См. `proposal.md — Why` про причины и порядок (сначала ядро, затем каждый плагин отдельным изменением).

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение ядра в виде спецификаций, пригодных как baseline для последующих изменений и как справочник при написании спецификаций плагинов.
- Разбить ядро на capability-границы, которые естественно соответствуют существующим файлам/классам, чтобы плагинные спецификации могли на них ссылаться (например, «использует `core/event-dispatch` для рассылки событий»).

**Non-Goals:**
- Изменение кода ядра — это change документирует существующее поведение as-is, без рефакторинга.
- Спецификации плагинов — они выносятся в отдельные changes, по одному на плагин.

## Decisions

- **Границы capability по классам, не по namespace целиком.** Вместо одной большой спецификации `core` — четыре: `core/application-bootstrap` (`HomeApplication`, `HomeConfiguration`), `core/plugin-model` (`PluginBase`, `IServiceContext`/`ServiceContext`, `PluginsOrder`), `core/event-dispatch` (`SafeInvoke`/`SafeInvokeAsync`, `EventContext`), `core/object-registry` (`BaseRegistry`/`ObjectRegistry`/`ObjectSetRegistry`/`BaseConfigurationBuilder`, рефлексивные хелперы `FindAttrs`/`FindMethods` из `Extensions`). Альтернатива — одна спецификация на весь namespace — была отклонена: она смешала бы независимо используемые плагинами возможности (не каждый плагин, скорее всего, будет одинаково ссылаться на bootstrap и на реестры) и была бы неудобна для последующих точечных изменений.
- **Спецификации описывают поведение, наблюдаемое разработчиком плагина, а не внутренние детали реализации.** Публичные классы ядра (`PluginBase`, `IServiceContext`, реестры) — это API, который плагины используют напрямую, поэтому их публичные контракты и есть «наблюдаемое поведение» для целей OpenSpec, а не внутренняя реализация. Детали вроде конкретного использования `Task.Run` или `ConcurrentDictionary` в спецификации не включены — это опустилось до уровня «как», а не «что».

## Risks / Trade-offs

- Baseline-спецификации пишутся по факту чтения кода без дополнительных тестов ядра — есть риск разойтись с фактическим поведением в неочевидных деталях (например, поведение при гонках в `ObjectSetRegistry`). Митигация: спецификации сформулированы по коду и комментариям в нём (`copy-on-write`, обработка исключений), при расхождении в будущем — исправляются по факту репорта.
- Дробление на 4 capability увеличивает число файлов спецификаций для небольшого по объёму кода. Считаем это оправданным ради возможности ссылаться на конкретную возможность из будущих плагинных спецификаций.
