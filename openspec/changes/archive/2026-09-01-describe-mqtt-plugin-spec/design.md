## Context

`Mqtt` — следующий по очереди плагин после `Mail` (см. `proposal.md — Why`). Он не зависит от других ещё не описанных плагинов системы, кроме уже специфицированного `Scripts` (атрибут `[ScriptCommand]`, тип `Buffer`, `plugins/scripts/script-events` для пользовательских событий).

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение `MqttPlugin` (конфигурация подключения, жизненный цикл клиента, приём и диспетчеризация сообщений, декларативная регистрация обработчиков топиков другими плагинами, регистрация подписок из `scriptEvents`, публикация сообщений из сценариев) как baseline-спецификацию.

**Non-Goals:**
- Изменение кода плагина — документируется поведение as-is.
- Повторное описание контрактов `[ScriptCommand]`, `Buffer` и пользовательских сценарных событий — они уже специфицированы в `plugins/scripts/script-execution` и `plugins/scripts/script-events`; спецификация `Mqtt` только ссылается на них.
- Описание внутреннего устройства библиотеки MQTTnet (протокол MQTT, детали её API) — фиксируется только наблюдаемое поведение плагина.

## Decisions

- **Три capability вместо одной.** В отличие от `Mail` (единственный контракт — отправка почты), `Mqtt` объединяет три различных по природе контракта: подключение/приём сообщений (`broker-connection`), декларативный механизм регистрации обработчиков другими плагинами (`topic-subscriptions`, аналогично `plugins/timer/callback-scheduling` и `plugins/scripts/script-events` — регистрация через атрибут), и исходящую публикацию из сценариев (`publishing`, симметрично разделению `inbound-message-handling`/`outbound-messaging` у `plugins/telegram-bot`). Разделение делает каждую спецификацию тестируемой независимо и позволяет другим будущим спецификациям (например, `NooLite`, который тоже может использовать `[ConfigureMqtt]`) ссылаться точечно на `topic-subscriptions`, не утягивая детали подключения.
- **`topic-subscriptions` включает и атрибут `[ConfigureMqtt]`, и регистрацию из `scriptEvents`.** Оба механизма используют один и тот же билдер (`MqttConfigurationBuilder`) и одну и ту же структуру данных (`ObjectRegistry` подписок по фильтру топика), различаясь только источником регистрации (код плагина против конфигурации). Это один контракт «как регистрируется обработчик топика», а не два.
- **Диспетчеризация входящих сообщений — часть `broker-connection`.** Хотя обработчики регистрируются через `topic-subscriptions`, факт получения сообщения от брокера и его маршрутизация по идентификаторам подписок — часть жизненного цикла соединения с брокером, симметрично тому, что `plugins/timer/callback-scheduling` включает и регистрацию таймеров, и их срабатывание.
- **Ошибки публикации пробрасываются вызывающему сценарию** (в отличие от `Mail`, где ошибки отправки поглощаются). Это фиксируется как наблюдаемое поведение кода (`Publish` вызывает `PublishAsync(...).GetAwaiter().GetResult()` без перехвата исключений, с комментарием в коде о намеренном ожидании результата, чтобы ошибка «долетела» до вызывающего кода), а не переосмысливается.

## Risks / Trade-offs

- Спецификация написана по чтению кода без тестов и README плагина (ни того, ни другого в репозитории нет для `Mqtt`) — возможны расхождения в неочевидных деталях (например, точное поведение MQTTnet при параллельных попытках переподключения). Митигация: формулировки ограничены поведением, видимым в коде плагина, без домыслов о внутренностях MQTTnet.
- Интервал периодической проверки соединения (60000 мс, атрибут `[TimerCallback(60000)]`) — конкретное значение не зафиксировано в спецификации как контракт (см. `docs-declare-contract-only` — спецификация не описывает тайминги реализации), только сам факт периодической проверки и переподключения.
