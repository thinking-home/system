## Context

`openspec/specs/core/*` описывает ядро, `openspec/specs/plugins/database/*` — плагин `Database`. `WebServer` — следующий по очереди плагин без внешних плагинных зависимостей (см. `proposal.md — Why`): он не зависит от `Database` или других плагинов, а от него будут зависеть Cron+WebApi+WebUi, Mail, Mqtt, NooLite, TelegramChatList+WebApi, WebUi. `WebServer.UrlValidation` — отдельный плагин, зависящий от `WebServer` через конструктор (`UrlValidationPlugin(WebServerPlugin server)`) и проверяющий по контракту `WebServer` все URL, которые зарегистрировали остальные плагины к моменту его `InitPlugin`.

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение `WebServerPlugin` (регистрация HTTP-ресурсов, обработка запросов, порт, шина сообщений) и `UrlValidationPlugin` (правила именования URL, публикация списка ошибок) как baseline-спецификацию, на которую смогут ссылаться будущие плагинные changes.
- Разбить `WebServer` на две capability по независимым потребителям контракта: HTTP-ресурсы (регистрация и обработка запросов) и шина сообщений (SignalR hub). `UrlValidation` — отдельная capability как отдельный плагин со своим контрактом.

**Non-Goals:**
- Изменение кода плагинов — документируется поведение as-is.
- Спецификации плагинов, использующих `WebServer` (Cron, Mail, Mqtt, NooLite, TelegramChatList, WebUi и др.) — выносятся в отдельные последующие changes.
- Описание ASP.NET Core/Kestrel/SignalR как таковых — они внешние зависимости; специфицируется только то, как плагины их используют.

## Decisions

- **Три capability вместо одной.** `http-resources` описывает контракт для авторов HTTP-обработчиков (регистрация статических/динамических ресурсов, формат запроса и ответа, обработка ошибок, порт) — то, на что будут ссылаться спецификации плагинов, предоставляющих HTTP API или статику. `message-bus` описывает независимый контракт клиент-серверной шины сообщений (SignalR) — используется только теми плагинами, которым нужен push на клиент. Разделение позволяет будущим плагинным спецификациям ссылаться точечно на нужную часть, не утягивая за собой детали другой. `url-validation` — отдельная capability, потому что это отдельный плагин со своим собственным жизненным циклом и контрактом (публикует список ошибок по HTTP), опирающийся на `http-resources` как потребитель.
- **URL-правила из README `UrlValidation` — часть контракта `url-validation`, а не `http-resources`.** `WebServerPlugin` технически не ограничивает формат URL (принимает любую строку). Правила формирования URL (plugin alias, префиксы `/api`, `/dynamic`, `/static`, `/vendor`, требования к расширению) — это конвенция, которую опционально проверяет `UrlValidationPlugin`, если он подключён. Поэтому она специфицируется как контракт `url-validation`, а не как ограничение `http-resources`.
- **Шина сообщений — не транспорт-независимая абстракция, а конкретно протокол SignalR.** Изначально предполагалось специфицировать только наблюдаемое поведение (доставка сообщений по топикам), не называя транспорт. Пересмотрено: шина не универсальна — подключиться к ней может только SignalR-клиент, а не произвольный WebSocket/HTTP-клиент, и на этом факте будут строиться будущие клиентские реализации (WebUi и другие плагины с клиентской частью). Поэтому `message-bus` явно специфицирует протокол как SignalR-based и фиксирует формат взаимодействия как часть контракта: маршрут hub-эндпоинта, имя клиентского метода доставки сообщений и его аргумент (объект `{guid, timestamp, topic, data}`), имя серверного метода отправки и его аргументы, а также рекомендуемый таймаут переподключения — все они публикуются как константы, на которые обязаны полагаться клиенты, а не быть захардкожены отдельно (подтверждается использованием этих констант в `ThinkingHome.Plugins.WebUi/WebUiPlugin.cs`, который передаёт их в конфигурацию клиента). Внутренние детали самого протокола SignalR (handshake, кодирование invocation-сообщений) по-прежнему не специфицируются — это ответственность SignalR-клиента, а не контракт `WebServer`.

## Risks / Trade-offs

- Спецификация написана по чтению кода и README без дополнительных тестов плагинов (тестов на `WebServer`/`UrlValidation` в репозитории нет) — возможны расхождения в неочевидных деталях. Митигация: формулировки опираются на фактический код и README; при расхождении в будущем — уточняются по факту.
