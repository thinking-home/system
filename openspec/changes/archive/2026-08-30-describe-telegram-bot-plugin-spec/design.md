## Context

`TelegramBot` — следующий по очереди плагин после `Timer` (см. `proposal.md — Why`). Он не зависит от других плагинов проекта, опирается на инфраструктуру ядра — модель плагина (`core/plugin-model`), поиск методов-обработчиков по атрибуту и реестр по ключу (`core/object-registry`, `FindMethods`/`ObjectSetRegistry`) — и на стороннюю библиотеку `Telegram.Bot`. От `TelegramBot` в дальнейшем зависит `TelegramChatList` (следующий change в очереди).

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение `TelegramBotPlugin` (авторизация по логину, разбор команды, событие `OnMessageReceived`, диспетчеризация в обработчики `[TelegramMessageHandler]`, отправка текста/фото/файлов) как baseline-спецификацию для будущих плагинных changes.

**Non-Goals:**
- Изменение кода плагина — документируется поведение as-is.
- Повторное описание изоляции ошибок обработчика/подписчика на уровне механизма — плагин использует `SafeInvoke`/`SafeInvokeAsync`, наблюдаемый эффект (ошибка одного обработчика не мешает другим) зафиксирован в спецификации плагина как поведенческое требование, без ссылки на конкретный вспомогательный API ядра (в отличие от `Timer`, эти хелперы не описаны отдельной core-спецификацией).
- Спецификация `TelegramChatList` и других плагинов, использующих `TelegramBot`, — выносится в отдельные последующие changes.

## Decisions

- **Две capability вместо одной.** У `TelegramBot`, в отличие от `Timer`, два разнородных публичных контракта: приём/диспетчеризация входящих сообщений (`inbound-message-handling`) и отправка исходящих (`outbound-messaging`). Они независимы друг от друга (можно только отправлять или только принимать), поэтому разделены — по аналогии с тем, как `web-server` разделён на `http-resources` и `message-bus`.
- **Событие `OnMessageReceived` описано отдельным требованием, до авторизации.** По коду и README событие возникает для всех входящих сообщений, включая неавторизованные и групповые чаты, — раньше проверки логина и типа чата. Это явно зафиксировано, чтобы не создавалось впечатление, что событие тоже фильтруется по `authorizedLogins`.
- **Пустая строка как валидное значение команды.** Атрибут `[TelegramMessageHandler("")]` и обработчик `ALL_COMMANDS` (атрибут без параметра) — разные случаи: первый совпадает только с сообщениями без команды, второй вызывается всегда. Оба случая зафиксированы отдельными сценариями в требовании о регистрации обработчиков.
- **Отправка не специфицируется на уровне конкретных методов Telegram Bot API.** Требования описывают наблюдаемый эффект («отправляется запрос на отправку X в чат Y»), а не факт вызова конкретного метода клиента (`SendMessage`/`SendPhoto`/`SendDocument`) — это деталь реализации, использующая стороннюю библиотеку.

## Risks / Trade-offs

- Спецификация написана по чтению кода и README; тесты плагина покрывают только разбор команды (`ParseCommand`), остальное поведение (авторизация, диспетчеризация, отправка) не покрыто тестами и специфицировано по коду. Митигация: формулировки опираются на фактический код и README; при расхождении в будущем — уточняются по факту.
