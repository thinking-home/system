## Неблокирующие находки

1. `openspec/changes/chat-list-ui/test-plan.md:88` и `:91` (проверка 8 «Ошибка загрузки списка чатов») — шаг «посмотреть уведомления и лог приложения» и ожидание «в логе есть запись об ошибке» указывают не на то место. Клиентский логгер оболочки собирается с единственным приёмником `ConsoleLogDestination` (`ThinkingHome.Plugins.WebUi/frontend/index.tsx:30-31`, реализация — `ThinkingHome.Plugins.WebUi/frontend/utils/logger.ts:25-42`): `useLogger().log(...)` пишет в консоль браузера и никуда не отправляет на сервер, в `logs/{Date}.log` (Serilog) записи не появится. Сценарий отказа: проверяющий смотрит серверный лог, не находит записи и помечает проверку проваленной при корректной работе раздела (либо, наоборот, принимает серверную запись об ошибке API за требуемый след). Наименьшая правка: в шаге и ожидаемом результате заменить «лог приложения» на «консоль браузера (вкладка Console)». Оракул: в консоли строка вида `<ISO-время> ERROR /TELEGRAM-CHAT-LIST: <сообщение>`. Само утверждение спецификации («показывается уведомление об ошибке, список не отображается») проверкой покрыто, поэтому находка неблокирующая.
2. `openspec/changes/chat-list-ui/test-plan.md:36-38` (проверка 1 «Раздел использует HTTP API списка чатов») — часть ожидаемого результата «прямых обращений к базе из раздела не происходит» в браузере не наблюдаема: из вкладки «Сеть» видно только HTTP-запросы, а обращение раздела к БД (если бы оно было) произошло бы внутри процесса. Сценарий отказа: проверка отмечается пройденной без реального основания, и вторая половина требования «Зависимость от HTTP API списка чатов» («SHALL не обращаться к базе данных напрямую») остаётся непроверенной. Наименьшая правка: добавить в проверку статический шаг — в `ThinkingHome.Plugins.TelegramChatList.WebUi.csproj` нет `ProjectReference` на `ThinkingHome.Plugins.Database` и на `ThinkingHome.Plugins.TelegramChatList` (состав ссылок зафиксирован в `design.md`, D1). Оракул: список `ProjectReference` нового проекта = `Core.Plugins`, `WebServer`, `WebUi`; в «Сети» единственный источник данных о чатах — `GET /api/telegram-chat-list/web-api/list`.
3. `openspec/changes/chat-list-ui/test-plan.md:100-111` (проверки 10 и 11) — обе проверки локализации выполняются только при `culture: ru-RU`, а часть требования «Локализация раздела списка чатов» (`specs/.../web-ui/spec.md:70`: «язык текстов по умолчанию — английский») ни одной проверкой не закрыта. Формально сценариев на английский язык в дельте нет, поэтому `coverage.yaml` полон, но пропуск дешёвый и реальный: расхождение ключей `Keyset('en', …)` и `Lang/TelegramChatListWebUiPlugin.resx` при русской культуре не проявится. Наименьшая правка: добавить в проверку 10 второй прогон с `culture: en-US` (или без ключа `culture`). Оракул: заголовок, подписи колонок и сообщение пустого списка — английские тексты кейсета (`There are no chats yet`), имён ключей (`title`, `emptyList`) на экране нет.
4. `openspec/changes/chat-list-ui/test-plan.md:59-60` (проверка 4 «Список отсортирован по убыванию даты») — ожидание «порядок не совпадает с порядком записей в ответе API» зависит от неконтролируемого условия: ресурс `/api/telegram-chat-list/web-api/list` сортировки не задаёт (`ThinkingHome.Plugins.TelegramChatList.WebApi/TelegramChatListWebApiPlugin.cs:20-21` — `Select(...).ToArray()` без `OrderBy`), порядок строк определяет PostgreSQL. Сценарий отказа: если ответ API случайно придёт уже по убыванию даты, проверяющий по букве ожидаемого результата пометит проверку проваленной, хотя раздел работает верно. Наименьшая правка: сделать главным ожиданием «строки идут по убыванию `date` (первой — `alpha`, 2026-05-20)», а несовпадение с порядком ответа API — дополнительным наблюдением с оговоркой «если порядки совпали, изменить порядок вставки записей и повторить». Оракул: порядок строк `alpha` → `bravo` → запись с `chatId = 1004` → `charlie` при любом порядке в ответе API.
