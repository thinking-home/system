## Context

`openspec/specs/core/*` уже описывает ядро. `ThinkingHome.Plugins.Database` — первый плагин без зависимостей от других плагинов (см. `proposal.md — Why`), от которого напрямую или транзитивно зависит большинство остальных (Scripts, Cron, TelegramChatList и др.). Плагины берутся в порядке использования — сначала плагины без зависимостей от других плагинов, чтобы более поздние плагинные спецификации могли ссылаться на уже описанные.

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение `DatabasePlugin` (подключение, миграции, API для других плагинов) как baseline-спецификацию, на которую смогут ссылаться будущие плагинные changes (Scripts, Cron, TelegramChatList и др.).
- Разбить плагин на две capability, соответствующие двум разными потребителями контракта: приложение/окружение (настройка подключения и миграции) и другие плагины (API регистрации модели и доступа к данным).

**Non-Goals:**
- Изменение кода плагина — документируется поведение as-is.
- Спецификации плагинов, использующих `DatabasePlugin` (Scripts, Cron и др.) — выносятся в отдельные последующие changes.
- Описание библиотеки `ThinkingHome.Migrator` как таковой — она внешняя зависимость; специфицируется только то, как `DatabasePlugin` её использует (что и когда мигрирует).

## Decisions

- **Две capability вместо одной.** `connection-and-migrations` описывает поведение, важное для окружения приложения (конфигурация, отказ при её отсутствии, применение миграций при старте) — то, что должен знать оператор/деплой. `data-access-api` описывает контракт для авторов плагинов (`[DbModelBuilder]`, `OpenSession`) — то, на что будут ссылаться спецификации других плагинов, хранящих данные в БД. Разделение позволяет плагинным спецификациям (например, Scripts, Cron) ссылаться точечно на `data-access-api`, не утягивая за собой детали миграций.
- **PostgreSQL — текущее ограничение реализации, а не часть контракта для потребителей.** Код жёстко использует `PostgreSQLProviderFactory`/`UseNpgsql`; поддержка нескольких СУБД — открытая задача в `TODO.md` («сделать поддержку нескольких СУБД»), но не текущее поведение. `connection-and-migrations` фиксирует, что сейчас поддерживается только PostgreSQL, явным отдельным требованием — это факт об окружении/деплое, не расширяемая точка. При этом `data-access-api` отдельно требует, чтобы контракт для плагинов-потребителей (`[DbModelBuilder]`, `OpenSession`) оставался выражен в терминах EF Core и не завязывался на специфику PostgreSQL — так более поздние плагинные спецификации не будут закладывать зависимость от конкретной СУБД, и переход на другую СУБД в будущем не потребует пересмотра их контрактов.
- **Рекомендация: не использовать FK-ограничения БД на таблицы других плагинов.** `ApplyMigrations()` мигрирует плагины по одному в порядке `DependencyIndex` (см. `core/plugin-model`), и для каждого плагина сразу применяет ВСЕ его миграции до последней, прежде чем переходить к следующему. Поэтому FK-ограничение зависящего плагина A на таблицу плагина B всегда ссылается на ТЕКУЩУЮ (последнюю) схему B, а не на ту, что была на момент написания миграции A. Будущая миграция B, переименовывающая или удаляющая столбец/таблицу, может сломать миграцию A — как на чистой БД (A попытается создать FK на несуществующий объект), так и на существующей (FK от A может помешать миграции B, изменяющей структуру таблицы, на которую ссылается FK). Проверка существующих миграций (`Cron`, `Scripts`, `TelegramChatList`, `Tmp`) показала, что сейчас все FK — внутриплагинные (`Scripts.Model.Migrations.Migration02/03`: `Scripts_EventHandler.UserScriptId → Scripts_UserScript.Id`, оба конца в одном плагине); межплагинных FK в коде нет. Рекомендация для авторов будущих плагинов: не создавать FK-ограничения БД на таблицы других плагинов — хранить только «мягкую» ссылку (обычный `Guid`/значение без `Database.AddForeignKey`) и при необходимости проверять целостность на уровне кода; формальные FK оставлять только внутри одной сборки/плагина, где один автор синхронно мигрирует обе связанные таблицы (как сейчас в Scripts). Альтернатива — разрешать межплагинные FK и трактовать таблицы плагина как часть его публичного контракта наравне с `[DbModelBuilder]`/`OpenSession` — отклонена: она обязывала бы каждый плагин версионировать схему БД как публичный API и явно поддерживать обратную совместимость таблиц, что сейчас нигде не описано и не проверяется.

## Risks / Trade-offs

- Спецификация написана по чтению кода без дополнительных тестов плагина — возможны расхождения в неочевидных деталях (например, порядок вызова `DbModelBuilder`-методов при равных `DependencyIndex`). Митигация: формулировки опираются на фактический код (`SelectMany`, `HashSet` по `asm.FullName`), при расхождении в будущем — уточняются по факту.
- Межплагинный FK на таблицу другого плагина ломается будущей миграцией этого плагина (переименование/удаление ссылаемого столбца или таблицы) → митигация: рекомендация выше (Decisions) — не создавать FK на таблицы чужих плагинов, использовать мягкие ссылки. На момент этого изменения нарушений в коде не найдено.
