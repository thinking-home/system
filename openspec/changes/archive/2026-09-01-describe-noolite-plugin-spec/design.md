## Context

`NooLite` — следующий по очереди плагин после `Mqtt` (см. `proposal.md — Why`). Он не зависит от других ещё не описанных плагинов системы: использует уже специфицированные `plugins/timer/callback-scheduling` (`[TimerCallback]` для переподключения), `plugins/scripts/script-execution` (`[ScriptCommand]`) и `plugins/scripts/script-events` (`[ConfigureScriptEvents]`, `ScriptEventEmitter`). Взаимодействие с адаптером MTRF-64-USB выполняется через внешний NuGet-пакет `ThinkingHome.NooLite` (`MTRFXXAdapter`), не входящий в этот репозиторий.

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение `NooLitePlugin` и `AdapterWrapper` (конфигурация порта, жизненный цикл адаптера и переподключение, декларативная регистрация обработчиков входящих данных другими плагинами, API управления нагрузкой/RGB-лентой для плагинов и сценариев, сценарные события) как baseline-спецификацию.

**Non-Goals:**
- Изменение кода плагина — документируется поведение as-is.
- Повторное описание контрактов `[TimerCallback]`, `[ScriptCommand]`, `[ConfigureScriptEvents]`/`ScriptEventEmitter` и изоляции ошибок обработчиков — они уже специфицированы в `plugins/timer/callback-scheduling`, `plugins/scripts/script-execution`, `plugins/scripts/script-events` и `core/event-dispatch`; спецификация `NooLite` только ссылается на них.
- Описание внутреннего протокола nooLite/nooLite-F и деталей API пакета `ThinkingHome.NooLite` (`MTRFXXAdapter`) — фиксируется только наблюдаемое поведение плагина поверх этого пакета.

## Decisions

- **Четыре capability вместо одной.** `NooLite` объединяет четыре разных по природе контракта: жизненный цикл соединения с адаптером (`device-connection`), декларативная регистрация обработчиков входящих данных другими плагинами (`data-handlers`, аналогично `plugins/scripts/script-events` — регистрация через атрибут), исходящее управление нагрузкой для плагинов и сценариев (`adapter-control`) и сценарные события о входящих данных (`script-events`). Такое разделение симметрично `plugins/mqtt` (`broker-connection`/`topic-subscriptions`/`publishing`) и делает каждую спецификацию тестируемой независимо.
- **`data-handlers` и `script-events` разделены, хотя оба реагируют на одни и те же входящие данные.** `data-handlers` — это прямой вызов Delegate-обработчиков, зарегистрированных другими плагинами через атрибуты (плагинный API, работает независимо от наличия `Scripts`), а `script-events` — это генерация сценарных событий через `ScriptEventEmitter`, доступная только если загружен `Scripts`. Это два разных механизма подписки на одни данные, симметрично тому, как в `NooLitePlugin.OnReceiveData` оба пути вызываются независимо друг от друга.
- **`adapter-control` описывает и плагинный, и сценарный API одним контрактом.** `AdapterWrapper` — единственный класс, реализующий обе поверхности (методы `PascalCase` для плагинов и обёртки `camelCase` для сценариев, вызывающие те же методы), различие только в именовании методов, а не в поведении.
- **Точное значение интервала переподключения и код 20000 мс (`[TimerCallback(20000)]`) не зафиксированы в спецификации как контракт** (см. память `docs-declare-contract-only` — спецификация не описывает тайминги реализации), только сам факт периодической попытки переподключения.

## Risks / Trade-offs

- Спецификация написана по чтению кода и README плагина (`ThinkingHome.Plugins.NooLite/README.md`), без тестов — возможны расхождения в неочевидных деталях поведения внешнего пакета `ThinkingHome.NooLite` (например, точная семантика `device.Open()` при уже открытом соединении). Митигация: формулировки ограничены поведением, видимым в коде плагина и README, без домыслов о внутренностях пакета.
