## Purpose

Описывает контракт `CronPlugin` — хранение записей расписания, периодическую проверку наступления времени их запуска и уведомление об этом обработчиков плагинов и сценариев автоматизации.

## ADDED Requirements

### Requirement: Хранение записи расписания
Запись расписания SHALL храниться как `CronTask` с полями: `Id` (идентификатор), `Name` (название для отображения, обязательно), `EventName` (имя пользовательского сценарного события, опционально), `Expression` (выражение cron, обязательно), `Enabled` (признак активности записи).

#### Scenario: Поля записи расписания
- **WHEN** сохраняется запись расписания
- **THEN** она содержит `Id`, `Name`, `EventName`, `Expression` и `Enabled`

### Requirement: Формат выражения cron
`Expression` SHALL задавать время запуска выражением cron из пяти сегментов (минута, час, день, месяц, день недели), разбираемым по правилам NCrontab: сегмент может содержать `*` (любое значение), число, диапазон (`1-5`), шаг (`*/5`) или список значений через запятую (`1,15,30`).

#### Scenario: Корректное выражение из пяти сегментов
- **WHEN** `Expression` записи задан в формате `минута час день месяц день-недели` (например, `*/5 * * * *`)
- **THEN** выражение распознаётся и используется для вычисления времени запуска записи

### Requirement: Периодическая проверка расписания
Плагин SHALL проверять расписание раз в 20 секунд (см. `plugins/timer/callback-scheduling` — регулярный вызов обработчика по таймеру) и определять, какие включённые (`Enabled = true`) записи должны быть запущены в текущей проверке.

#### Scenario: Наступление плановой проверки
- **WHEN** наступает момент очередной проверки расписания
- **THEN** плагин проверяет все включённые записи расписания на предмет наступления времени их запуска

### Requirement: Окно активных запусков
Запись расписания SHALL быть запущена в текущей проверке, если её ближайшее плановое время выполнения после нижней границы окна проверки наступило не позже текущего момента. Нижняя граница окна первой после старта приложения проверки SHALL быть равна текущему моменту минус 5 минут — так плановые запуски, время которых уже наступило (но не более чем 5 минут назад), выполняются при первой проверке после старта. Нижняя граница окна каждой следующей проверки, на которой были запуски, SHALL быть равна моменту предыдущей такой проверки — так один и тот же плановый момент не запускается повторно на следующих проверках.

#### Scenario: Плановое время в пределах 5 минут после старта приложения
- **WHEN** приложение запускается, и ближайшее плановое время выполнения записи расписания уже наступило, но не более чем 5 минут назад
- **THEN** запись запускается на первой после старта проверке расписания

#### Scenario: Плановое время более 5 минут в прошлом
- **WHEN** приложение запускается, и ближайшее плановое время выполнения записи расписания наступило более чем 5 минут назад
- **THEN** запись не запускается на первой после старта проверке расписания

#### Scenario: Повторная проверка не запускает уже обработанный момент
- **WHEN** плановый момент записи расписания уже был обработан на одной из проверок
- **THEN** на последующих проверках этот же плановый момент повторно не запускает запись

### Requirement: Некорректное выражение в загруженной записи
Если `Expression` сохранённой записи не может быть разобран как выражение cron (например, изменён напрямую в БД в обход проверки HTTP API), эта запись SHALL быть пропущена при загрузке расписания, ошибка SHALL быть записана в лог, а загрузка остальных записей SHALL быть выполнена без прерывания.

#### Scenario: В БД есть запись с некорректным выражением
- **WHEN** расписание загружается, и одна из включённых записей содержит `Expression`, который не удаётся разобрать
- **THEN** эта запись пропускается с ошибкой в логе, а остальные записи загружаются и используются как обычно

### Requirement: Сброс кэша расписания
Плагин SHALL кэшировать загруженное из хранилища расписание в памяти и SHALL предоставлять метод `ReloadTasks()`, вызов которого сбрасывает кэш; расписание SHALL быть заново загружено из хранилища при следующей проверке после сброса.

#### Scenario: Вызов ReloadTasks после изменения данных
- **WHEN** данные о записях расписания в хранилище изменены, и после этого вызван `ReloadTasks()`
- **THEN** при следующей проверке расписания используются обновлённые данные

### Requirement: Регистрация обработчиков атрибутом `[CronHandler]`
Плагин SHALL при инициализации найти во всех загруженных плагинах методы, отмеченные атрибутом `CronHandlerAttribute`, и зарегистрировать каждый найденный метод как обработчик запуска записей расписания. Сигнатура метода SHALL соответствовать делегату `CronHandlerDelegate(Guid cronTaskId)`.

#### Scenario: Метод отмечен атрибутом `[CronHandler]`
- **WHEN** метод плагина отмечен атрибутом `[CronHandler]` и соответствует сигнатуре `CronHandlerDelegate`
- **THEN** этот метод регистрируется как обработчик запуска записей расписания

#### Scenario: Несколько плагинов с обработчиками
- **WHEN** атрибутом `[CronHandler]` отмечены методы в нескольких загруженных плагинах
- **THEN** каждый отмеченный метод каждого плагина регистрируется как обработчик

### Requirement: Уведомления при запуске записи расписания
При запуске записи расписания плагин SHALL: инициировать пользовательское сценарное событие с именем `EventName` записи (см. `plugins/scripts/script-events` — пользовательское событие), если `EventName` заполнен; асинхронно вызвать все зарегистрированные обработчики `[CronHandler]`, передав им `Id` запущенной записи; инициировать сценарное событие `cron:task:started` с параметром meta `taskId`, равным `Id` записи в виде строки. Инициация пользовательского события, вызов обработчиков `[CronHandler]` и инициация `cron:task:started` SHALL происходить независимо: ошибка в одном из обработчиков `[CronHandler]` SHALL не препятствовать вызову остальных обработчиков и инициации событий (см. `core/event-dispatch` — «Изоляция ошибок при вызове обработчика»).

#### Scenario: Запуск записи с заполненным EventName
- **WHEN** наступает плановое время записи расписания с непустым `EventName`
- **THEN** инициируется пользовательское сценарное событие с этим именем, вызываются все обработчики `[CronHandler]` с `Id` записи, и инициируется сценарное событие `cron:task:started` с meta `taskId` = `Id` записи

#### Scenario: Запуск записи без EventName
- **WHEN** наступает плановое время записи расписания с пустым (не заданным) `EventName`
- **THEN** пользовательское сценарное событие не инициируется, но обработчики `[CronHandler]` вызываются, и инициируется сценарное событие `cron:task:started` с meta `taskId` = `Id` записи

#### Scenario: Обработчик `[CronHandler]` бросает исключение
- **WHEN** один из вызванных обработчиков `[CronHandler]` бросает исключение
- **THEN** ошибка не прерывает вызов остальных обработчиков `[CronHandler]` и не блокирует инициацию пользовательского события и `cron:task:started`
