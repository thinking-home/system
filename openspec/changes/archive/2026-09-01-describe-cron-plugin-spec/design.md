## Context

`openspec/specs/plugins/scripts/*` уже описаны (baseline-спецификация `script-events` фиксирует контракт регистрации и инициации сценарных событий со стороны `ScriptsPlugin`). `Cron` — следующий по очереди плагин (см. `proposal.md — Why`): он зависит от `DatabasePlugin`, `ScriptsPlugin` и `TimerPlugin` (внедряются в конструктор `CronPlugin(DatabasePlugin database, ScriptsPlugin scripts)`, таймер используется через атрибут `[TimerCallback]`, уже специфицированный в `plugins/timer/callback-scheduling`). `Cron.WebApi` зависит от `DatabasePlugin` и `CronPlugin` и предоставляет HTTP API поверх `WebServer` (уже специфицирован в `plugins/web-server/http-resources`). `Cron.WebUi` не имеет собственных внедряемых зависимостей плагинов, но по README требует совместной установки с `Cron.WebApi`, т.к. вся работа с расписанием идёт через его HTTP API.

`Cron` — первый по очереди плагин, инициирующий собственные сценарные события через уже специфицированный контракт `plugins/scripts/script-events` (регистрация через `[ConfigureScriptEvents]`, инициация пользовательского события через `EmitUserEvent`); эти механизмы используются по ссылке, не переспецифицируются заново.

Выражения cron разбирает и исполняет библиотека NCrontab (внешняя зависимость); человекочитаемое описание строит библиотека CronExpressionDescriptor. Детали работы самих библиотек (грамматика сегментов сверх уже описанной в README, алгоритм построения текста описания) не специфицируются — специфицируется только наблюдаемое поведение плагинов, которые их используют.

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение `CronPlugin` (хранение записей расписания, периодическая проверка, окно активных запусков, обработчики `[CronHandler]`, инициация пользовательского и служебного `cron:task:started` сценарных событий) как капабилити `plugins/cron/task-scheduling`.
- Зафиксировать HTTP API `Cron.WebApi` (`plugins/cron/http-api`) и раздел веб-интерфейса `Cron.WebUi` (`plugins/cron/web-ui`) как капабилити, каждая — потребитель контракта предыдущей.

**Non-Goals:**
- Изменение кода плагинов — документируется поведение as-is.
- Спецификации плагинов, которые в будущем будут использовать `[CronHandler]` для собственных задач по расписанию (например, будильник) — они появятся в собственных будущих changes и будут ссылаться на этот контракт, а не дублировать его.
- Грамматика выражений cron сверх уже описанной в README `Cron` (сегменты, `*`, число, диапазон, шаг, список) и алгоритм построения человекочитаемого описания CronExpressionDescriptor — специфицируется только то, что плагины используют один и тот же парсер для исполнения и проверки, и что описание строится на языке системы.
- Детали хранения через `DatabasePlugin`/EF Core (`plugins/database/data-access-api`), таймера (`plugins/timer/callback-scheduling`) и HTTP-инфраструктуры (`plugins/web-server/http-resources`) — используются по ссылке, не переспецифицируются.

## Decisions

- **Три капабилити: `task-scheduling`, `http-api`, `web-ui`.** В отличие от `Scripts` (где `script-execution` и `script-events` — два независимых контракта с разными группами потребителей), у `Cron` нет отдельного механизма регистрации событий — плагин только использует уже специфицированный `plugins/scripts/script-events`; выделять для этого отдельную капабилити избыточно. `task-scheduling` объединяет хранение расписания, его проверку и все уведомления о запуске (события для плагинов через `[CronHandler]` и сценарные события) в одну капабилити — это единый наблюдаемый контракт плагина `CronPlugin`. `http-api` и `web-ui` — отдельные капабилити один-к-одному с плагинами `Cron.WebApi` и `Cron.WebUi`, по аналогии с `plugins/scripts/http-api`/`web-ui`.
- **Окно активных запусков специфицируется по наблюдаемому поведению, а не по внутренним переменным.** Код использует `lastEventTime` и `ACTIVE_PERIOD` для сглаживания повторных проверок; спецификация формулирует то же самое как наблюдаемое правило (нижняя граница окна проверки — не более 5 минут в прошлом при первой проверке после старта, момент предыдущей проверки с запусками — во всех остальных случаях), не называя внутренние поля.
- **Обработчики `[CronHandler]` и сценарные события — одна группа требований («Уведомления при запуске записи расписания»), а не отдельные капабилити.** Все три канала уведомления (пользовательское событие, `[CronHandler]`, `cron:task:started`) срабатывают на одно и то же условие и не имеют независимых потребителей, оправдывающих разделение.
- **Формат HTTP-ответов и обработка ошибок `http-api` не переспецифицируются** — полностью описаны контрактом `plugins/web-server/http-resources`. `http-api` специфицирует только сами эндпоинты: URL, параметры и семантику (включая сброс кэша расписания при изменении данных).

## Risks / Trade-offs

- Спецификация написана по чтению кода и README без дополнительных тестов плагинов (тестов на `Cron`/`Cron.WebApi`/`Cron.WebUi` в репозитории нет) — возможны расхождения в неочевидных деталях (в частности, точная логика окна активных запусков). Митигация: формулировки опираются на фактический код (`OnTimerElapsed`) и README; при расхождении в будущем — уточняются по факту.
- `task-scheduling` специфицирует контракт `[CronHandler]` только со стороны `CronPlugin` (регистрация, вызов, изоляция ошибок); поведение конкретных плагинов-обработчиков (что они делают с `cronTaskId`) не специфицируется — это будет частью их собственных будущих спецификаций.
