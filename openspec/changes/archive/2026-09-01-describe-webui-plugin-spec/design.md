## Context

`plugins/web-server/http-resources` и `plugins/web-server/message-bus` уже описаны — `WebUi` использует их как транспорт (`RegisterDynamicResource`/`RegisterEmbeddedResource` для раздачи документа и статики, опубликованные значения протокола шины сообщений для клиента). `WebUi` не имеет собственных внедряемых зависимостей плагинов в конструкторе — он собирает список разделов у других плагинов через `[ConfigureWebUi]` во время конфигурации веб-сервера. `Scripts.WebUi` (`plugins/scripts/web-ui`) и `Cron.WebUi` (`plugins/cron/web-ui`) уже специфицированы и по контракту требуют совместной установки с `WebUi` как транспортным плагином — эта спецификация задаёт сам этот транспортный контракт, на который они ссылаются.

Клиентская часть построена на общем UI-ките `@thinking-home/ui` (React, react-router, логирование, i18n-провайдер, контракты `Toaster`/`MessageHub`/`ApiClient`) поверх Mantine как библиотеки компонентов. Детали самого кита и Mantine не специфицируются — это внешние зависимости; специфицируется только наблюдаемое поведение оболочки, которую строит `WebUi` поверх них (какие данные загружаются, что видит и может сделать пользователь, что получает код раздела через контекст).

## Goals / Non-Goals

**Goals:**
- Зафиксировать серверный контракт регистрации разделов и раздачи связанной статики (`page-registration`) — на него уже ссылаются `plugins/scripts/web-ui` и `plugins/cron/web-ui`.
- Зафиксировать наблюдаемое поведение клиентской оболочки (`application-shell`): загрузку разделов по маршруту, тему, обработку ошибок, общий контекст выполнения раздела.

**Non-Goals:**
- Изменение кода плагина — документируется поведение as-is.
- Контракт `@thinking-home/ui`, Mantine, SignalR-клиента и других внешних библиотек — не переспецифицируется, используется по ссылке (для шины сообщений — на `plugins/web-server/message-bus`).
- Конкретные разделы, которые регистрируют другие плагины (`Scripts.WebUi`, `Cron.WebUi`) — уже специфицированы отдельно и не переописываются здесь.
- Формат раздачи ресурсов и предсжатых копий как таковой (какие заголовки, как выбирается кодировка) — уже специфицирован в `plugins/web-server/http-resources`, здесь используется по ссылке, не переспецифицируется.

## Decisions

- **Две капабилити: `page-registration` (сервер) и `application-shell` (клиент).** Это разные контракты для разных потребителей: `page-registration` — контракт для плагинов, которые хотят добавить раздел (аналог того, как `plugins/scripts` разделяет `script-execution`/`http-api`/`web-ui` по потребителям), `application-shell` — контракт для кода самих разделов и для пользователя браузера. Разделение по границе сервер/клиент также совпадает с границей исходного кода плагина.
- **Манифест vendor-модулей и предсжатые копии не переспецифицируются как формат** — специфицируется только наблюдаемый эффект (документ содержит рабочую import map, файлы из неё раздаются), а не структура манифеста `StaticManifest`, генерируемого сборкой `@thinking-home/ui`, — это деталь реализации.
- **Локализация — часть `page-registration`, а не отдельная капабилити.** Эндпоинт `/api/webui/lang` существует исключительно для того, чтобы загруженный раздел мог получить свои строки — неотделимая часть контракта раздачи раздела, аналогично тому, как хранение сценариев — часть `script-execution` в `plugins/scripts`.
- **Контекст выполнения раздела (`application-shell`) специфицирует только то, что раздел получает и обязан использовать (API-клиент, шину сообщений, уведомления, язык), а не форму этих объектов** — их программный контракт задаётся внешним китом `@thinking-home/ui`, здесь это внешняя зависимость.

## Risks / Trade-offs

- Спецификация написана по чтению кода без дополнительных тестов плагина (тестов на `WebUi` в репозитории нет) — возможны расхождения в неочевидных деталях (например, точные условия показа ошибки). Митигация: формулировки опираются на фактический код; при расхождении в будущем — уточняются по факту.
- `application-shell` описывает поведение, часть которого реализована сторонним китом `@thinking-home/ui` (i18n-провайдер, `ErrorBoundary`, логирование) — специфицируется только видимый эффект (что раздел получает язык, что ошибка раздела не роняет всё приложение), без привязки к тому, что именно эти конкретные библиотеки это обеспечивают.
