1. `openspec/changes/design-fixes/test-plan.md:7` — утверждение спецификаций и D1 о том, что пустое состояние появляется только после успешного пустого ответа, не имеет проверочного оракула для незавершённого запроса. Если реализация инициализирует данные пустым массивом и показывает empty до ответа API, все текущие конечные проверки пройдут, хотя пользователь увидит ложное отсутствие данных во время загрузки. Наименьшее исправление — добавить в `coverage.yaml` и ручной план проверку удерживаемого запроса для пяти асинхронных списков (`/scripts`, `/scripts/subscriptions`, `/cron`, `/telegram-chat-list`, `/page2`): пока обязательные запросы не завершены, не показываются empty, error или таблица, сохраняется loading; после пустого успешного ответа появляется только empty.
2. `openspec/changes/design-fixes/test-plan.md:9` — сценарии страницы подписок не проверяют полный инвариант `openspec/changes/design-fixes/specs/plugins/scripts/web-ui/spec.md:4`: заголовок должен оставаться видимым при пустом и ошибочном исходах, а действие добавления — также при ошибке. Реализация может поместить заголовок или кнопку внутрь ветки `ready`, пройти текущие проверки сообщения и уведомления, но нарушить спецификацию. Наименьшее исправление — дополнить проверки пустого и ошибочного исходов явным ожиданием видимого заголовка, а ошибочного исхода — доступной кнопкой добавления.
3. `openspec/changes/design-fixes/test-plan.md:10` — ручной сценарий проверяет отказ каждого из трёх запросов страницы подписок только по одному, поэтому не покрывает решение `design.md:98` и задачу `tasks.md:9` о единственном уведомлении при агрегированной начальной загрузке. Если два или три запроса завершатся ошибкой одновременно, независимые обработчики могут показать несколько уведомлений, а существующая проверка всё равно пройдёт. Наименьшее исправление — добавить в coverage и ручной план одновременную ошибку как минимум двух обязательных запросов и оракул: одно page-level error-состояние, ровно одно уведомление, список не отображается.
