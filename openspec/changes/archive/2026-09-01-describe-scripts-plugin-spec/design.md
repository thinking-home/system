## Context

`openspec/specs/plugins/database/*` и `openspec/specs/plugins/web-server/*` уже описаны. `Scripts` — следующий по очереди плагин (см. `proposal.md — Why`): он зависит только от `Database` (внедряется в конструктор `ScriptsPlugin(DatabasePlugin database)`), а от его контракта будут зависеть будущие плагинные спецификации, инициирующие сценарные события (Cron, Mail, Mqtt, NooLite, TelegramChatList). `Scripts.WebApi` зависит от `Database` и `ScriptsPlugin` и предоставляет HTTP API поверх `WebServer` (`ConfigureWebServer`, `HttpRequestParams`, `HttpHandlerResult` — уже специфицированы в `plugins/web-server/http-resources`). `Scripts.WebUi` не имеет собственных внедряемых зависимостей плагинов в конструкторе, но по контракту (README) требует совместной установки со `Scripts.WebApi`, т.к. вся работа со сценариями идёт через его HTTP API; сам он регистрирует страницы через `ConfigureWebUi` и раздаёт встроенный шрифт редактора через `ConfigureWebServer`.

Сценарии исполняются движком Jint (JavaScript-интерпретатор на .NET); детали работы самого движка (парсинг, таймаут интерпретации) не специфицируются — это внешняя зависимость, специфицируется только то, как плагин её использует (что таймаут прерывает выполнение с ошибкой, что для каждого запуска создаётся отдельный движок).

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение `ScriptsPlugin` (выполнение сценариев, объект `host`, регистрация и инициация сценарных событий, подписки с фильтрацией по meta) как baseline-спецификацию, на которую смогут ссылаться будущие плагинные changes, инициирующие сценарные события.
- Зафиксировать HTTP API `Scripts.WebApi` и разделы веб-интерфейса `Scripts.WebUi` как отдельные капабилити, каждая — потребитель контракта предыдущей.

**Non-Goals:**
- Изменение кода плагинов — документируется поведение as-is.
- Спецификации плагинов, использующих `Scripts` для инициации собственных сценарных событий (Cron, Mail, Mqtt, NooLite, TelegramChatList и др.) — выносятся в отдельные последующие changes; контракт `[ConfigureScriptEvents]` специфицируется только со стороны `ScriptsPlugin` (регистрация, инициация, доставка), а не перечислением конкретных событий других плагинов.
- Детали самого JavaScript-движка Jint (грамматика языка, внутренняя работа таймаута интерпретации) — специфицируется только наблюдаемое поведение со стороны `ScriptsPlugin` (что сценарий — JavaScript, что доступны `args`/`meta`/`host`, что таймаут прерывает выполнение).
- Детали хранения через `DatabasePlugin`/EF Core (уже специфицированы в `plugins/database/data-access-api`) и HTTP-инфраструктуры (`plugins/web-server/http-resources`) — используются по ссылке, не переспецифицируются.

## Decisions

- **Четыре капабилити: `script-execution`, `script-events`, `http-api`, `web-ui`.** `script-execution` — контракт для любого кода (плагинов и других сценариев), который хочет выполнить сценарий или предоставить сценариям метод/данные (`[ScriptCommand]`, `Buffer`); это ядро, не зависящее от событий. `script-events` — независимый контракт для плагинов, которые хотят зарегистрировать собственное сценарное событие и инициировать его; он использует `script-execution` (выполнение сценария-обработчика), но потребители у него другие — не тот, кто просто хочет выполнить сценарий, а тот, кто хочет реагировать на действия в системе через сценарии. Разделение по образцу `plugins/web-server` (`http-resources`/`message-bus`) — независимые потребители получают точечную ссылку. `http-api` и `web-ui` — отдельные капабилити один-к-одному с плагинами `Scripts.WebApi` и `Scripts.WebUi`, `web-ui` явно ссылается на `http-api` как на свою зависимость (аналогично тому, как в README `Scripts.WebUi` явно требует `Scripts.WebApi`).
- **Хранение сценариев (`UserScript`) — часть `script-execution`, а не отдельная капабилити.** Модель существует исключительно для того, чтобы сценарий можно было выполнить по имени/id (`ExecuteScriptByName`, `ExecuteScript(UserScript)`) — это неотделимая часть контракта выполнения, а не самостоятельная возможность хранения данных.
- **Хранение подписок (`ScriptEventHandler`) и фильтрация по meta — часть `script-events`.** Подписка существует только в контексте инициации и доставки сценарных событий; выносить её в `script-execution` или в отдельную капабилити нет отдельных потребителей.
- **Формат HTTP-ответов и обработка ошибок `http-api` не переспецифицируются** — они полностью описаны контрактом `plugins/web-server/http-resources` (`HttpHandlerResult`, `HttpHandlerException`, обязательные параметры). `http-api` специфицирует только сами эндпоинты: URL, параметры, семантику и форму данных в ответе.

## Risks / Trade-offs

- Спецификация написана по чтению кода и README без дополнительных тестов плагинов (тестов на `Scripts`/`Scripts.WebApi`/`Scripts.WebUi` в репозитории нет) — возможны расхождения в неочевидных деталях. Митигация: формулировки опираются на фактический код и README; при расхождении в будущем — уточняются по факту.
- `script-events` специфицирует только контракт со стороны `ScriptsPlugin`; поведение конкретных плагинов-владельцев событий (какие события они регистрируют, что кладут в meta) будет описано в их собственных будущих спецификациях и не дублируется здесь.
