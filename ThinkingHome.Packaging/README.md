# Упаковка и проверка плагинов

Инструмент создаёт NuGet-пакет плагина и проверяет его метаданные и публичный контракт без выполнения кода DLL. Готовый пакет появляется в выходном каталоге только после успешной проверки.

## Быстрый запуск

Из корня репозитория:

```powershell
dotnet build ThinkingHome.Packaging/ThinkingHome.Packaging.csproj -m:1 -p:UseSharedCompilation=false
dotnet run --project ThinkingHome.Packaging/ThinkingHome.Packaging.csproj --no-build -- pack ThinkingHome.Plugins.Timer/ThinkingHome.Plugins.Timer.csproj artifacts/plugin-packages
```

Команда собирает выбранный проект в Release, выполняет стандартный NuGet pack во временную папку, проверяет архив и переносит его в выходной каталог. Существующий файл той же версии не перезаписывается. При ошибке временная папка удаляется, ранее созданные пакеты сохраняются. Пакеты никуда не публикуются.

При разработке в ограниченном окружении можно добавить `-p:NuGetAudit=false` к команде сборки; это не часть проверки контрактов. Внутренняя сборка плагина выполняется последовательно без сервера компиляции.

## Подключение проекта

В конце csproj импортируйте `build/ThinkingHome.Plugin.targets`. Плагин ссылается на ядро обычным PackageReference или ProjectReference:

```xml
<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
</PropertyGroup>
<ItemGroup>
  <PackageReference Include="ThinkingHome.Core.Plugins" Version="4.0.0-alpha34" />
</ItemGroup>
<Import Project="../ThinkingHome.Packaging/build/ThinkingHome.Plugin.targets" />
```

Ссылка на ядро нужна для компиляции `PluginBase` и вызовов общих API. Стандартная сборка сохраняет ссылки на сборки в DLL, а NuGet — зависимость и диапазон версии в nuspec. При установке менеджер сопоставляет требование плагина с ядром, предоставленным хостом. Ядро не копируется в пакет плагина. Если нужна верхняя граница совместимости, задайте её в обычном NuGet-диапазоне; например, `[4.0.0-alpha34,5.0.0)`.

Путь импорта задаётся относительно проекта. ID и версия берутся из стандартных `PackageId` и `PackageVersion`; диапазоны зависимостей — из стандартных PackageReference и ProjectReference через NuGet. Отдельный JSON-манифест не создаётся. Точки входа обнаруживаются автоматически в основной DLL: публичные неабстрактные классы-наследники PluginBase без открытых generic-параметров. Учитываются косвенное наследование и публичные вложенные классы. Зависимости не сканируются. Если подходящих классов нет, проверка плагина завершается ошибкой. Правило одинаково для упаковки, установки и локального запуска; анализ метаданных не выполняет код плагина.

Для каждой прямой неплатформенной пакетной зависимости укажите классификацию по package ID:

```xml
<ItemGroup>
  <PackageReference Include="Some.Library" Version="1.2.3" />
  <ThinkingHomeDependency Include="Some.Library" Kind="private" />
</ItemGroup>
```

Поддерживаются `private`, `shared` и `plugin`. Классификация описывает использование зависимости и не заменяет её версию. `shared` требуется, когда библиотечные типы входят в публичный контракт. `plugin` обозначает ссылку на другой плагин. Пакетные зависимости не копируются в пакет плагина.

Необъявленные транзитивные неплатформенные зависимости считаются приватными. Если такая библиотека участвует в публичном контракте, добавьте прямую ссылку и явно объявите `shared`. Валидатор не повышает видимость зависимостей автоматически.

Платформа определяется через [общий API](../ThinkingHome.Platform/README.md): ядро и его транзитивные зависимости из стандартного `.deps.json`, а также фактические сборки .NET и ASP.NET Core. Упаковщик использует платформу своего комплекта инструментов; окончательную совместимость с целевым хостом проверяет планировщик. Автор плагина не задаёт состав платформы. Общие targets передают валидатору только сведения о сборке плагина: ссылки, владельцев DLL, framework и путь к `project.assets.json`.

## Встроенные библиотеки и ресурсы

Библиотеку, которая не поставляется отдельным пакетом, объявите явно:

```xml
<ItemGroup>
  <ThinkingHomeEmbedded Include="vendor/MyHelper.dll" Kind="private" />
  <None Include="Resources/settings-template.txt" Pack="true" PackagePath="content/settings-template.txt" />
</ItemGroup>
```

Имя файла встроенной managed-библиотеки должно совпадать с simple assembly name. Targets добавляет ссылку для компиляции, метаданные и файл в `lib/net10.0/`. Не добавляйте ту же DLL повторно через None/Content. Допустим также `Kind="shared"`; к её типам применяются правила общего контракта.

Обычные ресурсы DLL и satellite-сборки формирует SDK, вспомогательные файлы включаются стандартными Pack/PackagePath. Необъявленные дополнительные DLL и встроенные копии платформенных или пакетных библиотек отклоняются.

## Что проверяется

- Наличие ровно одной входной DLL с манифестом версии 1; уникальные и известные ключи, обязательные поля и допустимые значения.
- Совпадение package ID и версии между DLL и nuspec, наличие объявленных зависимостей и соответствие восстановленных версий диапазонам nuspec.
- Конкретные доступные классы PluginBase в точках входа, включая проверку принадлежности базового класса ядру.
- Public/protected API доступных типов: результаты и параметры, поля, свойства, базовые классы, интерфейсы, обобщённые аргументы и ограничения, делегаты и события, атрибуты и их аргументы, перенаправленные типы.
- Транзитивная поверхность доступных DTO, в том числе из внешней общей библиотеки. Приватные поля реализации не считаются публичным контрактом.
- Разрешимость внешних ссылок и принадлежность сборок пакетам по данным SDK и project.assets.json. Несовпадение имени DLL и package ID допустимо.
- Состав пакета, отсутствие дубликатов имён и небезопасных путей в архиве.

Пример ошибки:

```text
Fixture.TransitivePlugin.GetData -> return.get_Items -> return -> element -> Vendor.Dependency.Item:
private dependency Fixture.Dependency (Vendor.Dependency) crosses plugin boundary
```

Исправление — убрать приватные библиотечные типы из контракта либо явно объявить библиотеку общей и согласовать версии с потребителями.

## Повторная проверка пакета

Публичный API `PackageValidator.Validate(packagePath, inputsDirectory)` и команда `validate` позволяют проверить уже собранный архив. Окружение сборки предоставляет SDK: разрешённые ссылки, их владельцы, assets-файл и framework. Каталог платформы определяется общим API текущего процесса.

Для диагностической подготовки архива и окружения можно использовать внутренний маршрут:

```powershell
dotnet pack path/to/Plugin.csproj -c Release -o artifacts/check -m:1 -p:UseSharedCompilation=false -p:ThinkingHomePackaging=true -p:ThinkingHomeValidationDirectory=D:/absolute/path/to/artifacts/check/inputs
dotnet run --project ThinkingHome.Packaging/ThinkingHome.Packaging.csproj --no-build -- validate artifacts/check/Plugin.1.0.0.nupkg artifacts/check/inputs
```

Это внутренний маршрут для диагностики и тестов: промежуточный пакет может быть некорректным. Для обычной поставки используйте команду `pack` инструмента; прямой `dotnet pack` подключённого проекта без внутреннего флага завершается подсказкой. Флаг не является границей безопасности.

[Планировщик](../ThinkingHome.PackagePlanning/README.md) повторно применяет общий ContractValidator к выбранным runtime-сборкам и явному каталогу платформы. Файлы окружения не входят в пакет и не принимаются на доверии из его содержимого. Валидатор проверяет контракты против восстановленного окружения сборки, а не вычисляет новый граф версий.

## Границы текущей реализации

Поддерживается один framework `net10.0`, одна входная DLL и managed-ресурсы в `lib/net10.0`, включая локализацию. Дополнительно допускаются DLL в `runtimes/<rid>/lib/net10.0` и `runtimes/<rid>/native`. Упаковщик проверяет базовый managed-контракт; выбранный RID-вариант повторно проверяет планировщик перед получением плана. Базовая входная DLL в `lib/net10.0` остаётся обязательной. Файлы без расширения DLL не используются для подтверждения managed-контрактов.

Валидатор не выполняет код плагина, но команда упаковки запускает сборку доверенного проекта. Это не песочница для чужих MSBuild-проектов. Проверка приватных значений, спрятанных за `object` или динамическими каналами, не входит в MVP. Планировщик проверяет обычные зависимости от ядра и остальных пакетов относительно библиотек, предоставленных хостом. Отдельного диапазона версий платформы в манифесте нет.

Все 19 плагинов монорепозитория подключены к общим targets и объявляют маркер плагина и классификацию зависимостей. Интеграционные тесты упаковки и HTTP-поставки охватывают Timer, WebServer и WebServer.UrlValidation.

## Проверки


```powershell
dotnet test ThinkingHome.Packaging.Tests/ThinkingHome.Packaging.Tests.csproj -m:1 -p:UseSharedCompilation=false -p:NuGetAudit=false
```

Тесты собирают настоящие корректные и ошибочные nupkg в `artifacts/packaging-tests`. Корректный плагин содержит бросающий исключение module initializer: успешная проверка подтверждает отсутствие выполнения его кода. Также проверяются утечки контрактов, встроенная библиотека, повреждённые метаданные, изменённый nuspec, недостающая ссылка и сохранение старого пакета при ошибке. Папка artifacts не включается в git.

Для запуска из IDE упаковка не нужна: обычный Build создаёт DLL, deps.json и копирует зависимости. Общие targets включают GenerateDependencyFile и CopyLocalLockFileAssemblies. [Локальное подключение к хосту](../ThinkingHome.PackageRuntime/README.md).
