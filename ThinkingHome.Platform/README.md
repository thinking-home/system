# Общая платформа хоста и менеджера

`ThinkingHome.Platform.HostPlatform.Current()` возвращает `PlatformCatalog` текущего процесса: версию ядра, целевой .NET/RID, предоставляемые пакеты и пути к сборкам. Это общий API двух отдельных программ — хоста и менеджера пакетов. Он не запускает другой процесс, не загружает плагины и не читает или записывает `platform.json`.

## Контракт поставки

Хост и менеджер поставляются и обновляются одним комплектом. В комплекте должны совпадать версия ядра, целевой .NET и архитектура, framework references, правила выбора runtime и фактические версии платформенных библиотек. Совпадения только `net10.0` недостаточно. Настройки запуска не должны выбирать разный runtime для двух программ.

Текущая поставка использует .NET 10 и ASP.NET Core 10. Общая библиотека содержит FrameworkReference на Microsoft.AspNetCore.App, поэтому оба исполняемых проекта получают одинаковые требования к runtime. Публикация `ThinkingHome.Console` включает менеджер, его deps.json/runtimeconfig.json и общие зависимости. Поставляется весь результат публикации; отдельные DLL или файлы runtimeconfig между версиями не подменяются.

Менеджер обслуживает установку своего комплекта поставки. Параметр каталога приложения выбирает данные и конфигурацию, а не другую версию хоста. Управление произвольной другой версией системы внешним менеджером не поддерживается.

## Состав платформы

API включает фактически используемые сборки .NET и ASP.NET Core, ядро ThinkingHome.Core.Plugins и его транзитивные зависимости из стандартного `.deps.json` процесса. Обход начинается с ядра: собственные зависимости хоста и менеджера, например System.CommandLine и NuGet.Protocol, не становятся контрактом плагинов.

Идентификаторы и версии обычных пакетов берутся из графа `.deps.json`, имена их DLL — из runtime-ресурсов пакета. ID пакета не обязан совпадать с именем сборки. Для библиотек общих frameworks каталог предоставляет имена сборок и фактические версии продукта. Состав framework берётся из его `.deps.json`, фактические пути DLL — из данных runtime. Это учитывает зависимости, которые SDK исключает из графа приложения, поскольку их уже предоставляет framework, а также пакетные версии framework-библиотек в каталоге приложения.

Упаковщик использует тот же API для классификации платформенных зависимостей. Стандартная сборка и публикация SDK создают все необходимые данные; дополнительные генераторы и ручные перечни не нужны. Отсутствующая зависимость ядра приводит к ошибке определения платформы.

`RuntimeFiles` изолирует обращение к служебным свойствам хоста .NET `TRUSTED_PLATFORM_ASSEMBLIES` и `APP_CONTEXT_DEPS_FILES`. Это имена интерфейса runtime, а не настройки приложения. Если runtime не предоставляет необходимые сведения, API возвращает понятную ошибку. Поддерживается обычная поставка с общими .NET/ASP.NET Core frameworks; single-file, trimming и NativeAOT не поддерживаются.

Менеджер передаёт полученный каталог планировщику, хост — загрузчику. Lock-файл содержит версии и контрольные суммы платформенных сборок для проверки совместимости. При расхождении платформы `validate`, `ci` и запуск хоста завершаются ошибкой. После обновления комплекта или runtime может потребоваться пересчитать план установкой плагинов; locked-восстановление не подбирает новую платформу автоматически.

Низкоуровневые API планировщика и менеджера принимают `PlatformCatalog` явно: это позволяет тестировать совместимость и встраивать их в инструменты. Пользовательским командам менеджера файл платформы не нужен.

Совместимость плагина с ядром задаётся обычной зависимостью от `ThinkingHome.Core.Plugins`: диапазоном NuGet в пакете или версией из deps.json локальной сборки. Отдельного диапазона версии платформы в манифесте плагина нет. Поле `Version` каталога идентифицирует поставку в lock-файле и не задаёт дополнительного ограничения для плагинов.
