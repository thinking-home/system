# Интеграция плагинов с хостом

Один `ThinkingHome.Console` запускает установленные пакеты, локальные сборки и их сочетание. Специальных режимов разработки, отдельного хоста монорепозитория и упаковки перед локальным запуском нет. Отличаются входные источники, а проверка графа, контрактов и загрузчик общие.

## Декларация и поиск

Установленный набор хранится в `.thinkinghome`: корневые плагины, lock, карта загрузки и генерируемая конфигурация. Дополнительно хост автоматически читает необязательный `plugins.local.json` в каталоге приложения:

```json
{
  "pluginPaths": [
    "../MyPlugin/bin/Debug/net10.0/MyPlugin.dll"
  ],
  "plugins": [
    { "id": "MyPlugin", "version": "[1.0.0]" }
  ]
}
```

`pluginPaths` — доступные локальные реализации. Идентификатор и версия читаются из метаданных DLL, а не из имени файла. Подключение пути само по себе не включает плагин. `plugins` — дополнительные корни приложения; запись с тем же ID явно заменяет ограничение установленного корня только на этот запуск. Если нужен лишь локальный вариант уже установленного плагина, поле `plugins` можно опустить. Оба массива по умолчанию пустые; `null`, неизвестные поля и дубли корней — ошибки.

Относительные пути считаются от `plugins.local.json`. Рабочая папка терминала/IDE не меняет их смысл. `--app` задаёт каталог приложения; без него используется каталог исполняемого файла хоста. В этом же каталоге находятся `.thinkinghome` и пользовательские appsettings. Конфигурация подключений — строгий JSON; комментарии в ней не поддерживаются.

Для каждого требуемого ID алгоритм:

1. Выбирает явно подключённую локальную реализацию, если она есть.
2. Иначе выбирает плагин из проверенного установленного состояния.
3. Проверяет версию, требуемую платформу и зависимости и продолжает обход.
4. Проверяет итоговый граф, циклы, единственность версий плагинов, identity сборок и статические контракты.
5. Строит карту загрузки и загружает точки входа, обнаруженные при статической проверке основной DLL.

Две локальные реализации одного ID — ошибка, даже если указан один файл дважды. Несовместимая или повреждённая локальная сборка не приводит к молчаливому переключению на установленную. Соседние DLL плагинов, скопированные через ProjectReference, не подключаются неявно: их нужно явно перечислить или установить соответствующий плагин менеджером. Это сохраняет одну активную реализацию каждого плагина.

Все явно перечисленные подключения должны быть корректными сборками плагинов с метаданными и `.deps.json`. Обычная библиотека не может стать корнем или локальным плагином. Хост не сканирует текущую папку, PATH или все DLL своего bin; случайный файл не меняет состав приложения.

## Откуда берутся зависимости

Для установленного пакета источником истины остаётся проверенный lock и содержимое хранилища. Хост удерживает один снимок установки на всё время выполнения и проверяет именно его; повреждённое установленное состояние блокирует запуск, даже если некоторые плагины заменяются локальными.

Для локального плагина нужны результаты обычного `dotnet build`:

- DLL с тем же манифестом AssemblyMetadata, который используется при поставке пакета;
- соседний `.deps.json` с графом зависимостей сборки;
- библиотеки и файлы runtime, скопированные SDK в выходной каталог;
- PDB для отладки, если они не встроены в DLL.

Общие [ThinkingHome.Plugin.targets](../ThinkingHome.Packaging/build/ThinkingHome.Plugin.targets) включают `GenerateDependencyFile` и `CopyLocalLockFileAssemblies`. Никакой nupkg, публикации или установки собственной DLL для запуска не требуется. При нестандартном копировании файлов нужно сохранить структуру SDK, включая каталоги культур и `runtimes`.

Зависимости-плагины распознаются по метаданным подключённых DLL и установленных пакетов и разрешаются общим поиском по ID. Соседняя DLL с маркером плагина распознаётся как требование отдельного подключения, но не подключается автоматически. Библиотеки приватные по умолчанию; ThinkingHomeShared на обычной ссылке делает библиотеку общей. Утечки приватных типов по-прежнему запрещены. Библиотеки локального плагина берутся из его результата сборки, а библиотеки установленного — из зафиксированного хранилища. Необъявленная копия библиотеки не подхватывается. Платформа предоставляет свои сборки единственным владельцем; локальная копия ядра или библиотек платформы не заменяет их.

Важная граница текущего формата: `.deps.json` содержит уже разрешённые версии, а не исходные NuGet-диапазоны. Поэтому локальные зависимости от плагинов и библиотек фиксируются на версии, с которыми выполнен Build. Требования к платформенным пакетам проверяются как минимальные версии. При смене версии стороннего плагина нужно обновить reference и пересобрать свой проект. Версия самой локальной DLL проверяется по ограничению корня или требующего её плагина. Это сознательная консервативная проверка, без догадок о потерянных верхних границах диапазонов.

Хост не обращается к HTTP-репозиториям и не восстанавливает NuGet-пакеты при старте. Недостающая зависимость останавливает запуск с цепочкой требований. Установка сторонних плагинов выполняется менеджером пакетов, восстановление зависимостей проекта — SDK при сборке.

## Один план загрузки

Локальный запуск формирует временный план в памяти. Упаковки, временной установки и копирования исполняемых DLL в отдельное окружение нет: загружаются исходные файлы результата Build. Статическая проверка может использовать временные копии для анализа метаданных; они удаляются до запуска.

`ExecutionPlanner` адаптирует результаты Build и установленные файлы к общему `PlanBuilder`. `ExpandGraph`, проверка ссылок и `ContractValidator` используются повторно. Менеджер пакетов не знает о локальных подключениях. Его install/ci/validate не читают `plugins.local.json`; полную проверку реально запускаемой комбинации выполняет хост `--check`.

План выполнения не сохраняется как новый lock и не меняет указатель установленного состояния. `ci` продолжает восстанавливать опубликованные версии с исходными хешами. Локальные сборки могут меняться после Build без изменения версии; их метаданные и хеши перечитываются на следующем запуске. Исполняемый файл повторно проверяется по хешу непосредственно перед первой загрузкой. Собирать используемые DLL следует после остановки процесса: на Windows они могут быть заблокированы.

Каждая managed-сборка имеет одного владельца:

- платформа — Default AssemblyLoadContext;
- общие библиотеки — общий контекст;
- плагин и его приватные библиотеки — контекст этого плагина.

Импорт чужого плагина возвращает его сборку из контекста владельца. Поэтому тип в параметре конструктора, тип регистрации DI и фактический экземпляр совпадают. Две приватные версии библиотеки могут существовать в разных контекстах. Общая библиотека должна иметь одну совместимую версию. Различающееся содержимое одной и той же библиотеки одной версии в выбранном графе отклоняется.

Статическая проверка до выполнения кода исследует public/protected API, типы параметров/результатов, наследование, обобщения, делегаты, события и атрибуты. Приватный тип не может пересечь границу плагина. Значения, скрытые за object или динамическими каналами, эта проверка не отслеживает.

Спутники локализации выбираются с учётом культуры. Native-ресурсы выбираются по RID; в локальном `.deps.json` варианты для других платформ игнорируются, как альтернативы результата SDK. Файлы из карты разрешаются по точному пути; системные native-библиотеки разрешает ОС. Наличие плана не гарантирует наличие всех внешних системных native-зависимостей.

## Домашний сервер

Нужны .NET 10 и ASP.NET Core runtime. Потребительский хост не ссылается на проекты плагинов:

```powershell
dotnet publish ThinkingHome.Console/ThinkingHome.Console.csproj -c Release -o ./artifacts/host
New-Item -ItemType Directory -Force ./artifacts/application
```

Создайте `sources.json` по [формату источников](../ThinkingHome.PackageSources/README.md). Плагин соответствующей версии предварительно публикуется в вашем репозитории:

```powershell
dotnet ./artifacts/host/ThinkingHome.PackageManagement.dll install ./artifacts/application ThinkingHome.Plugins.Timer "[4.0.0-alpha34]" ./artifacts/application/sources.json
dotnet ./artifacts/host/ThinkingHome.Console.dll --app ./artifacts/application --check
dotnet ./artifacts/host/ThinkingHome.Console.dll --app ./artifacts/application
```

Хост и менеджер входят в один комплект публикации и обновляются вместе. Каждый получает платформу непосредственно через общий API `ThinkingHome.Platform.HostPlatform.Current()`, без файла и запуска другой программы. Версии ядра, runtime и платформенных библиотек должны совпадать; после обновления может потребоваться пересчитать план. [Контракт совместной поставки](../ThinkingHome.Platform/README.md).

## Автор плагина в IDE

1. Создайте отдельный каталог приложения для отладки и задайте его через `--app`.
2. Установите туда сторонние плагины через менеджер пакетов. Проект собственного плагина должен ссылаться на их контракты для компиляции.
3. Добавьте `plugins.local.json` с путём к выходной DLL и корнем собственного плагина.
4. Настройте обычный Build проекта перед запуском. Запускайте из отладчика `dotnet <host>/ThinkingHome.Console.dll --app <каталог>` или подключите отладчик к этому процессу.
5. Остановите процесс, пересоберите проект и запустите снова после изменений.

Отладчик использует DLL и PDB прямо из каталога проекта. Не нужны отдельные версии пакета на каждую сборку. Несколько собственных плагинов подключаются несколькими путями тем же способом. Локальная реализация зависимости имеет приоритет над установленной и подчиняется тем же проверкам версий.

## Разработчик монорепозитория

[ThinkingHome.Local.proj](../ThinkingHome.Local.proj) — автоматизация сборки, не дополнительный хост. Она собирает проекты плагинов и Console и создаёт обычный `plugins.local.json` в выходной папке Console. Пути получает через MSBuild `GetTargetPath`; каждый плагин загружается из собственного каталога. ID проектов этого монорепозитория совпадают с PackageId, версия берётся из Package.xml.

```powershell
dotnet msbuild ThinkingHome.Local.proj -m:1 -p:UseSharedCompilation=false -p:NuGetAudit=false
dotnet ThinkingHome.Console/bin/Debug/net10.0/ThinkingHome.Console.dll --check
```

При первой сборке чистого репозитория выполните сборку дважды: существующие frontend-targets требуют второго прохода для включения впервые сгенерированных UI-ресурсов в DLL (см. [правила сборки](../.sbox/project/testing.md)).

После уже выполненной сборки решения можно только обновить подключения:

```powershell
dotnet msbuild ThinkingHome.Local.proj -t:WriteConnections
```

В IDE стартовый проект — **ThinkingHome.Console**. Один раз подготовьте подключения указанной командой; при изменении состава проектов, Configuration или выходных путей обновите их. Для автоматического обновления настройте `ThinkingHome.Local.proj` как pre-launch задачу. При неизменных путях достаточно обычного Build изменённых проектов. Общая папка со всеми DLL не используется для разрешения плагинов.

Для пользовательских настроек можно задать `THINKINGHOME_ENVIRONMENT=Development`; это стандартный выбор appsettings, он не меняет алгоритм загрузки. Существующий appsettings.Development.json копируется Console при сборке. Обычный запуск всех плагинов требует настроенных БД, брокера и других внешних сервисов. `--check` их не запускает.

Все 19 проектов плагинов монорепозитория содержат маркер плагина и отметки ThinkingHomeShared на обычных ссылках; точки входа обнаруживаются автоматически. EF и его контрактные зависимости, Migrator.Framework, Telegram.Bot, ThinkingHome.NooLite и NCrontab объявлены общими там, где их типы участвуют в публичных контрактах. Библиотеки реализации сохраняют приватную область. Изменение такого контракта требует повторной проверки всего графа.

## Конфигурация, жизненный цикл и границы проверки

Менеджер сохраняет `appsettings.plugins.json` в поколении состояния и защищает его хешем. Хост формирует эквивалентный источник из фактического плана выполнения, затем накладывает appsettings.json, appsettings.{THINKINGHOME_ENVIRONMENT}.json и переменные THINKINGHOME_. Настройки пользователя не переписываются. Поле `assemblies` не используется для поиска/регистрации плагинов.

DI получает только проверенные entry points в порядке зависимостей. InitPlugin и StartPlugin выполняются в порядке создания экземпляров DI; StopPlugin — в обратном порядке для плагинов, инициализация которых началась, в том числе при ошибке старта. Сигнатуры атрибутных обработчиков проверяются при регистрации через CreateDelegate. Подписки хоста снимаются, контейнер освобождается, затем освобождается снимок установки.

Полный список параметров хоста, включая справку, приведён в [документации Console](../ThinkingHome.Console/README.md#параметры-командной-строки). Разбор и проверку аргументов до загрузки плагинов выполняет System.CommandLine.

`--check` проверяет файлы, граф и статические контракты и загружает типы. Он не создаёт экземпляры, не запускает init/start, не проверяет соединение с БД, аппаратурой и внешними API. Ошибки конфигурации/обработчиков, зависящие от жизненного цикла, могут обнаружиться только при обычном запуске.

Горячая замена не поддерживается. Контексты загрузки допускают освобождение после остановки, но внешние ссылки на типы и делегаты могут задерживать выгрузку. Загрузчик не является песочницей для недоверенного кода. Поддерживаемые цели MVP: net10.0/win-x64 и net10.0/linux-x64; single-file, trimming и NativeAOT не поддерживаются. Фактические проверки этой поставки и ограничения среды перечислены в [testing.md](../.sbox/project/testing.md).
