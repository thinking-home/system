# План установки плагинов

Планировщик разрешает версии и области загрузки, скачивает пакеты для проверки, выбирает runtime-файлы и повторно проверяет статические контракты на выбранных DLL. Результат — `plugins.lock.json` и связанный с ним `load-map.json`. Планирование не изменяет установленное состояние и appsettings.

## Запуск

Для обычной установки используйте [менеджер пакетов](../ThinkingHome.PackageManagement/README.md): он получает платформу автоматически из [общего API](../ThinkingHome.Platform/README.md). Приведённый ниже низкоуровневый CLI предназначен для инструментов и тестов с явно заданной платформой.

Из корня репозитория:

```powershell
dotnet build ThinkingHome.PackagePlanning/ThinkingHome.PackagePlanning.csproj -m:1 -p:UseSharedCompilation=false
dotnet run --project ThinkingHome.PackagePlanning/ThinkingHome.PackagePlanning.csproj --no-build -- plan plugins.json platform.json ThinkingHome.PackageSources/sources.example.json artifacts/plan
```

Выходной каталог должен отсутствовать. Оба документа сначала записываются в соседний временный каталог и становятся видимыми вместе после его переименования. Повторный запуск не перезаписывает существующий результат. Архивы и распакованные DLL используются для проверки, но не сохраняются как установленный набор пакетов; временные DLL удаляются.

Декларация корневых плагинов `plugins.json`:

```json
{
  "framework": "net10.0",
  "rid": "win-x64",
  "plugins": [
    { "id": "ThinkingHome.Plugins.Timer", "version": "[4.0.0-alpha34]" }
  ]
}
```

Версия — диапазон NuGet; квадратные скобки фиксируют точную версию. Поддерживаются `net10.0` и RID `win-x64`, `linux-x64`. Каждому целевому окружению нужен собственный каталог платформы и отдельный план.

## Каталог платформы

`platform.json` задаёт поставщик хоста, а не автор устанавливаемого плагина:

```json
{
  "version": "4.0.0-alpha34",
  "framework": "net10.0",
  "rid": "win-x64",
  "packages": {
    "ThinkingHome.Core.Plugins": "4.0.0-alpha34",
    "Microsoft.Extensions.Logging.Abstractions": "10.0.11"
  },
  "assemblies": [
    "host/ThinkingHome.Core.Plugins.dll",
    "host/Microsoft.Extensions.Logging.Abstractions.dll",
    "runtime/System.Private.CoreLib.dll"
  ]
}
```

Это сокращённый пример структуры: рабочий каталог должен перечислять все предоставляемые пакеты и все сборки .NET, ядра и общих контрактов, необходимые выбранным плагинам. Пути разрешаются относительно файла каталога. `System.Private.CoreLib` и `ThinkingHome.Core.Plugins` обязательны. Неявного дополнения DLL из bin процесса или распознавания платформы по префиксам нет.

Для минимального хоста можно опубликовать `ThinkingHome.Core.Plugins` в отдельную папку, взять список пакетов с точными версиями из его `.deps.json`, перечислить DLL этой папки и DLL целевого runtime .NET 10. Хост с ASP.NET или дополнительными общими контрактами должен явно добавить их поставку. Каталог для Linux должен описывать Linux-поставку, даже если план строится на Windows.

При планировании проверяются диапазоны обычных зависимостей, включая ядро и пакеты, предоставленные платформой, идентичности и хеши сборок. Абсолютные локальные пути в итоговые документы не попадают. Наличие указанного пакета в каталоге — доверенное утверждение поставщика платформы; каталог не принимается из скачанного плагина.

## Выбор версий и областей

- Корни ищутся только в репозиториях плагинов. Каждая неплатформенная зависимость сначала ищется там же; только отсутствие ID во всех репозиториях плагинов разрешает поиск в источниках библиотек. Маркер плагина проверяется в скачанной DLL. Несовместимая версия, повреждённый пакет и ошибка репозитория не разрешают переключение на библиотеку. Порядок внутри групп задаёт [клиент источников](../ThinkingHome.PackageSources/README.md).
- Выбирается максимальная допустимая стабильная версия. Prerelease включается, если хотя бы одно требование явно содержит prerelease-границу или prerelease-шаблон. При конфликте транзитивных требований поиск возвращается к другим кандидатам; лимит — 10000 ветвей. Сетевые ошибки и повреждённые архивы не подменяются версионным конфликтом.
- У каждого плагина одна версия и собственная область `plugin:<id>`. Типизированная ссылка на другой плагин импортирует его сборку из области владельца. Приватные DLL поставщика не импортируются.
- У явно общих библиотек одна версия в области `shared`. Их зависимости реализации разрешаются в той же области; это не делает типы этих зависимостей автоматически общим контрактом. Независимая приватная версия допустима в области другого плагина.
- Отметка shared на обычной ссылке применяется и к ссылкам на ту же библиотеку внутри графа владельца. Остальные библиотеки приватные по умолчанию; плагины определяются автоматически. В одной области невозможно одновременно связать одинаковое имя DLL с разными пакетами или владельцами.
- Циклы зависимостей плагинов отклоняются. План фиксирует порядок запуска: зависимости раньше потребителей. Ошибки версий содержат цепочки требований.

Одинаковые ID и версия хранятся в lock-файле один раз; разные области ссылаются на эту запись. Дедупликация файлов не объединяет экземпляры приватных сборок в памяти.

## Ресурсы и проверка контрактов

Совместимая framework-группа выбирается через `NuGet.Frameworks`. Для managed-кода приоритет имеют `runtimes/<rid>/lib/<tfm>`, затем `lib/<tfm>`; native-файлы выбираются из ближайшего `runtimes/<rid>/native`. Используется портативная цепочка RID для двух поддерживаемых целей. Каталоги разных вариантов не смешиваются; `_._` сохраняет смысл пустой группы. Локализованные `.resources.dll` сохраняют культуру и владельца.

`ref` не используется для выполнения. DLL с `ReferenceAssemblyAttribute`, несовместимой архитектурой, отсутствующими ссылками или конфликтующими именами отклоняются. Проверяются имена, версии, культура и public key token ссылок; меньшая выбранная AssemblyVersion не удовлетворяет большей запрошенной. Произвольные сборочные targets, install-скрипты и преобразования NuGet не выполняются: пакет должен содержать готовые ресурсы.

Пакеты с собственным `runtime.json` отклоняются: расширение RID-графа и дополнительные runtime-зависимости из этого файла пока не поддерживаются. Зависимости поддерживаемого профиля задаются через nuspec, готовые файлы — через стандартные каталоги runtime-ресурсов.

Выбранная runtime-DLL плагина должна иметь тот же манифест, что и базовая DLL пакета. Точки входа обнаруживает `PluginEntryPoints.Discover` в выбранной основной DLL: публичные неабстрактные наследники `PluginBase` без открытых generic-параметров. Список вычисляется после разрешения зависимостей и сохраняется в lock; автор не объявляет его в манифесте. Для локальных DLL применяется то же правило. Анализ публичного контракта выполняет общий `ContractValidator` в MetadataLoadContext. Код DLL и module initializer не выполняются. Проверка не доказывает совместимость всех вызовов в телах методов и отсутствие динамических утечек через `object`; эти обязанности и ограничения остаются у авторов пакетов.

Правила выбора ресурсов: [документация NuGet](https://learn.microsoft.com/en-us/nuget/create-packages/native-files-in-net-packages), [каталог RID .NET](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog).

## Форматы результата и API

`plugins.lock.json` версии 1 содержит целевую среду, корни, снимок платформы, точные версии и источники пакетов, SHA-512 архивов и файлов, узлы областей, рёбра с диапазонами и порядок плагинов. Исходные пути внутри архивов сохраняются.

`load-map.json` версии 1 содержит SHA-512 канонических JSON-байтов lock-файла, среду, managed/native/resource-привязки, владельцев, identity, культуру, пакет, относительный путь и хеш файла. Привязки платформы указываются через identity и хеш; локальные пути предоставляет хост. Карту нельзя независимо редактировать или использовать для нового выбора версий.

Публичный API: `PackagePlanner(IPackageSource).PlanAsync(PlanRequest, PlatformCatalog, CancellationToken)`. `NuGetSourceClient` реализует `IPackageSource`. Сериализация `PlanJson.Bytes` даёт стабильные байты для одинакового входа и пакетов; lock и карта не содержат времени создания и временных путей.

## Проверки

```powershell
dotnet test ThinkingHome.Packaging.Tests/ThinkingHome.Packaging.Tests.csproj -m:1 -p:UseSharedCompilation=false -p:NuGetAudit=false
```

Тесты используют реальные тестовые DLL и nupkg, проверяют приватные и общие версии, возврат при конфликте, плавающие версии, циклы, утечки типов, встроенные DLL, локализацию, выбор ресурсов обеих целевых сред, детерминизм и CLI через локальный HTTP-репозиторий. Проверки выбора Linux-файлов на Windows не заменяют запуск на Linux и исполнение native-кода.

План применяет [ThinkingHome.PackageManagement](../ThinkingHome.PackageManagement/README.md): хранилище, согласованная установка, locked-восстановление и валидация установленного состояния. `LockedPlanVerifier.Verify` проверяет точный граф без поиска новых версий. Загрузку плагинов выполняет [ThinkingHome.PackageRuntime](../ThinkingHome.PackageRuntime/README.md).

`ExecutionPlanner.Build` составляет план выполнения из проверенной установки и локальных DLL/deps.json. Он использует тот же граф и PlanBuilder/ContractValidator. Этот план хранится в памяти, содержит локальные пути через отдельную таблицу файлов и не является входом install/ci. [Формат подключений и правила версий](../ThinkingHome.PackageRuntime/README.md).

Locked-восстановление определяет плагины по метаданным зафиксированных архивов, проверяет отметки shared и весь граф заново. Поиска в репозиториях для классификации при этом нет. Одна активная версия каждого плагина и ошибки циклических зависимостей сохраняются.

`LockedPlanVerifier.RemovePlugin` проверяет исходный план и обратные зависимости, затем исключает неиспользуемый плагин и недостижимые узлы. Обход учитывает зависимости через библиотеки. Новый план строится из тех же зафиксированных архивов без обращения к источникам и изменения оставшихся версий; карты и статические контракты проверяются заново. Фиксацию результата выполняет `PackageManager.RemoveAsync`.
