# Контракты пакета и прототип загрузки плагинов

Исторический отчёт о прототипе. Актуальные правила метаданных описаны в [документации упаковщика](../../ThinkingHome.Packaging/README.md), [ADR-0004](decisions/ADR-0004-plugin-entry-point-discovery.md) и [ADR-0005](decisions/ADR-0005-core-package-compatibility.md).

Первый этап [плана MVP](decisions/ADR-0003-plugin-package-management-stages.md) уточняет технический контракт и проверяет модель из [ADR-0001](decisions/ADR-0001-plugin-package-management.md). Прототип находится в `prototypes/PluginLoading`, не подключён к рабочему решению и не заменяет загрузчик приложения.

## Контракт метаданных версии 1

Для первого формата выбираются строковые `AssemblyMetadataAttribute`: их можно читать непосредственно из PE-метаданных без загрузки DLL, зависимостей и исполнения конструкторов атрибутов. Специальная библиотека атрибутов для распознавания пакета не нужна.

| Ключ | Значение и правило |
|---|---|
| `ThinkingHome.Plugin.ManifestVersion` | `1`; отсутствующее поле означает отсутствие признака плагина, неизвестная версия отклоняется |
| `ThinkingHome.Plugin.PackageId` | ID содержащего пакета, совпадающий с nuspec |
| `ThinkingHome.Plugin.PackageVersion` | Версия пакета, совпадающая с nuspec; не заменяется AssemblyVersion |
| `ThinkingHome.Plugin.PlatformRange` | Допустимый диапазон версий контракта платформы ThinkingHome |
| `ThinkingHome.Plugin.EntryPoint.<полное имя типа>` | `plugin`; один или несколько конкретных классов PluginBase из этой DLL |
| `ThinkingHome.Plugin.Dependency.<package-id>` | `plugin`, `private` или `shared`; классификация прямой пакетной зависимости |
| `ThinkingHome.Plugin.Embedded.<simple-assembly-name>` | `private` или `shared`; встроенная библиотека внутри пакета |

Каждый ключ уникален. Отсутствие обязательных полей, повтор ключа, несуществующая точка входа и противоречие с nuspec — ошибки упаковки. Диапазоны пакетных зависимостей берутся из nuspec для выбранного framework, а не повторяются в строковых атрибутах. Framework определяется стандартными метаданными сборки и структурой пакета; RID — выбранными runtime-ресурсами.

Прототип содержит вручную заданные примеры этих атрибутов и проверяет чтение маркера, точки входа и классификации зависимости. Он не является реализацией упаковщика или полного валидатора. Его проекты используют ProjectReference; указанные package ID тестовых библиотек задают будущую пакетную идентичность, сами nupkg ещё не создаются. Генерация полей, согласование с nuspec, проверка типов точек входа и строгая обработка некорректного входа относятся к этапу 2.

Для каждой целевой группы ресурсов пакет содержит одну входную DLL с манифестом; вспомогательные сборки не объявляются отдельными плагинами. Несколько классов PluginBase внутри входной DLL допустимы: пакет устанавливается как единое целое. Один package ID не обязан совпадать с именем сборки; пакет может содержать несколько сборок. Соответствие устанавливается при анализе фактических runtime-ресурсов, а не угадывается по имени пакета.

Платформенные зависимости распознаются по каталогу предоставляемых хостом сборок и пакетов с версиями. Ссылка на такую зависимость не приводит к скачиванию приватной копии; проверяется совместимость с платформой. Разрешение имён исключительно по префиксам запрещено.

## Контракт областей загрузки

Ключ установки пакета — нормализованные ID и версия вместе с зафиксированным хешем. Ключ привязки сборки — область загрузки и simple assembly name. Карта дополнительно содержит полную identity сборки, package ID/version, относительный путь, хеш и владельца загрузки. Две несовместимые identity с одним simple name внутри одной области являются конфликтом ещё до запуска.

Владелец каждой сборки один: платформа, общая область либо конкретный плагин. Ссылка потребителя на другой плагин возвращает сборку из контекста владельца, не загружает её повторно. При вызове кода поставщика его приватные зависимости разрешаются в контексте поставщика.

Общие библиотеки имеют одну согласованную версию и загружаются совместно; приватная другая версия допустима в отдельной области. Замыкание типов общего API проверяется статически. Зависимости реализации общей библиотеки также должны иметь разрешённые привязки у её владельца; объявление общей только верхней DLL не заменяет разрешение её полного runtime-графа.

Для MVP платформа и общие библиотеки могут загружаться в Default по явной карте. Сборки плагинов имеют собственные контексты. Реальная интеграция должна запрещать случайное удовлетворение приватной зависимости библиотекой хоста. Fallback допускается только для явно разрешённой платформы; ошибка неизвестной зависимости не превращается в произвольный поиск по bin.

Объявленные диапазоны совместимости пакетов проверяет будущий резолвер. Правила версии AssemblyLoadContext не заменяют согласование NuGet-версий и проверку бинарных контрактов.

## Целевые платформы

Для реализации MVP принимается базовая матрица `net10.0`, `win-x64` и `linux-x64`: рабочая Windows-среда и Linux-поставка приложения. Поддержка ARM, macOS и других framework не входит в первоначальную матрицу. Это целевые платформы для последующей приёмки, а не утверждение уже проверенной совместимости.

Первый эксперимент выполняется на доступной Windows x64. Linux и native-ресурсы требуют отдельных прогонов перед приёмкой MVP. Прототип проверяет managed-загрузку; независимость native-библиотек, hot reload и выгрузка контекстов не проверяются.

## Состав эксперимента

| Проект | Назначение |
|---|---|
| PrivateV1 | Сборка Prototype.PrivateLibrary версии 1 с результатом `private-v1` |
| PrivateV2 | Сборка с тем же именем версии 2 с результатом `private-v2` |
| Provider | Плагин с прямой зависимостью от реального DatabasePlugin и приватной версии 1 |
| Consumer | Плагин с прямой зависимостью от Provider и приватной версии 2; обработчик DbModelBuilder |
| Harness | Отдельный исполняемый стенд с проверками, завершающийся ошибкой при нарушении ожиданий |

Harness не имеет compile-time ссылок на типы Provider и Consumer. Ссылка на проект Consumer с `ReferenceOutputAssembly=false` нужна только для сборки тестовых DLL. Для общего контракта стенд использует существующие зависимости репозитория, новые внешние пакеты не добавляются.

Реальный DatabasePlugin в эксперименте имеет явного владельца Default, поскольку стенд типизированно проверяет его API. Provider и Consumer находятся в отдельных контекстах. Это проверяет совместимость существующих API, но перенос DatabasePlugin и остальных реальных плагинов в динамическую загрузку хоста остаётся задачей этапа 6.

Проверки создают DbContext и ModelBuilder, находят настоящий атрибут и вызывают настоящий делегат. InitPlugin, StartPlugin, миграции, подключения к БД и прочие интеграции не запускаются.

## Воспроизведение

Из корня репозитория:

```powershell
dotnet build prototypes/PluginLoading/Harness/Harness.csproj -m:1 -p:UseSharedCompilation=false -p:NuGetAudit=false
dotnet run --project prototypes/PluginLoading/Harness/Harness.csproj --no-build -- D:/Source/system Debug
```

Первый аргумент стенда — абсолютный путь к корню конкретного checkout, второй — конфигурация сборки. Для другого каталога или Linux нужно передать соответствующий путь. Стенд использует только уже объявленные зависимости проекта; восстановление требует доступного NuGet-кеша или настроенных источников.

## Результат и пределы проверки

Проверка 2026-10-12: Windows x64, SDK 10.0.401, runtime 10.0.12, Debug. Сборка завершилась без предупреждений и ошибок; стенд прошёл 18 проверок:

- Чтение маркера, точки входа и категории зависимости из PE без загрузки плагина.
- Единая идентичность типа Provider и единственные экземпляры Provider, Consumer и реального DatabasePlugin через DI.
- Одновременная работа приватных версий 1 и 2 с одним именем сборки; разные identity их типов.
- Вызов Consumer → Provider сохраняет приватную версию Provider.
- Реальный DbContext передаётся через два плагина и остаётся совместим с типами хоста.
- Обработчик с реальным DbModelBuilderAttribute находится через существующий FindMethods, создаётся DbModelBuilderDelegate, успешно изменяющий общий ModelBuilder.
- Тестовые плагины и приватные библиотеки не попадают в Default; сборка Provider загружена ровно один раз.
- Необъявленная зависимость завершается ошибкой вместо неявного поиска.

Первый запуск сборки в окружении завершался без диагностики при параллельном восстановлении, а сервер компиляции ожидал недоступный канал. Последовательная сборка `-m:1` с `UseSharedCompilation=false` успешно обходит эти ограничения; изменения исходников продукта для этого не требуются.

Вывод: проверенные прямые ссылки, DI и существующий API обработчиков совместимы с выбранной моделью изоляции. Оснований требовать выделения всех контрактов в отдельные интерфейсные пакеты по результатам эксперимента нет. Это не доказательство совместимости всех существующих плагинов.

Полный резолвер, несовместимые диапазоны пакетов, статический анализ утечек, выбор native-ресурсов и работа HTTP-репозитория не входят в этот эксперимент и проверяются на соответствующих этапах плана.
