# Журнал приёмки опубликованного комплекта

## 15 октября 2026: Windows и подготовка WSL

Статус: цикл опубликованного комплекта на Windows прошёл; приёмка Linux не завершена. Windows потребовала перезагрузку после установки компонентов WSL, поэтому Linux-прогон не запускался.

Среда прогона: Windows x64, .NET SDK 10.0.401, Microsoft.NETCore.App и Microsoft.AspNetCore.App 10.0.12. Установлены WSL 3.0.1 и ядро 6.18.40.1; дистрибутив Linux и .NET внутри него ещё предстоит подготовить после перезагрузки. Автоматическая перезагрузка не выполнялась.

### Способ проверки

Сценарий [tools/package-acceptance.py](../../tools/package-acceptance.py) публикует комплект хоста/менеджера, сервер репозитория и упаковщик в новый каталог. Все потребительские команды запускаются через опубликованные DLL из этого каталога, а не через dotnet run или тестовый процесс. Каталоги приложения изначально пусты; plugins.local.json не используется.

Из исходников упакованы реальные Timer, WebServer и WebServer.UrlValidation. Дополнительный Acceptance.Probe версий 1.0.0 и 2.0.0 имеет типизированные ссылки на Timer/WebServer и приватную Newtonsoft.Json 13.0.3. Библиотека скачана менеджером с NuGet.org. HTTP-обработчик подтверждает версию работающего плагина и вызывает native-функцию GetCurrentProcessId, сравнивая результат с PID процесса. На Linux тот же сценарий использует getpid из libc; эта ветвь пока не проверена.

### Найденная и исправленная проблема

Стандартный dotnet publish включал локальный appsettings.Development.json, поскольку SDK наследовал CopyToOutputDirectory. Для этого файла задан CopyToPublishDirectory=Never; копирование при обычной сборке для отладки сохранено. Исходный пользовательский файл не менялся. В приёмочном сценарии и существующем CLI-тесте проверяется отсутствие этого файла и plugins.local.json в публикации. Обновлённый CLI-тест прошёл отдельно после исправления; проверены форматирование C#, синтаксис сценария Python и git diff --check. Полные 130 + 43 теста предыдущего этапа в этой приёмке повторно не запускались.

### Что ещё не подтверждено

Linux/WSL и Docker не запускались. Вызов системной native-функции не заменяет проверку загрузки native-библиотеки из NuGet-пакета. Этот прогон не проверял физические устройства, внешние БД, аппаратное отключение питания и сетевые файловые системы. Результат не закрывает Linux-часть этапа 7.

## 17 октября 2026: Linux в WSL2

Статус: опубликованный комплект прошёл все 28 шагов того же приёмочного сценария на Linux. Это закрывает Linux-прогон пакетного менеджера в WSL; проверка аппаратных интеграций в него не входит.

Подготовлена Ubuntu 24.04.5 LTS, WSL2, ядро 6.18.54.1-microsoft-standard-WSL2, x64. Из репозитория Ubuntu установлены .NET SDK 10.0.112, .NET/ASP.NET Core runtime 10.0.12 и Python 3. Запуск выполнен непривилегированным пользователем `acceptance`, из отдельной копии текущих исходников `/home/acceptance/system-20261017`, без Windows bin/obj и локальных настроек разработчика. Данные установки находятся в файловой системе Linux.

### Исправления по результатам прогона

1. Дистрибутивный .NET возвращает RID `ubuntu.24.04-x64`; менеджер раньше отклонял его, ожидая `linux-x64`. Общий API `HostPlatform.CurrentRid` нормализует Linux x64 и используется как при построении каталога платформы, так и при проверке запуска хоста. Исключения для musl/Alpine, Bionic и других архитектур сохранены.
2. Штатные ASP.NET Core DLL оказались Linux ReadyToRun: поле PE machine равно `AMD64 XOR 0x7B79`, а не обычному AMD64. Валидатор принимает этот вариант только для Linux x64 и при наличии сигнатуры ReadyToRun. Проверки x86-only и неподдерживаемых архитектур сохранены. Формат сверён с [исходным кодом CoreCLR .NET 10](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/coreclr/inc/pedecoder.h) и [описанием ReadyToRun](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/readytorun-format.md).

### Результаты

Все проверки таблицы Windows выше повторены в Linux: публикация и упаковка, установка через HTTP с реальным скачиванием Newtonsoft.Json, запуск плагинов с DI и приватной библиотекой, обновление работающей установки, перезапуск, locked-восстановление в пустой каталог, офлайн-валидация и ремонт, recover, отказ удаления используемой зависимости и удаление до пустого графа. Native-вызов `getpid` из libc вернул PID хоста. Работающий процесс продолжал использовать 1.0.0 после установки 2.0.0; после штатной остановки и перезапуска использовал 2.0.0. Пользовательский appsettings.json сохранён побайтово.

Успешный результат: `/home/acceptance/run-20261017-complete/result.json`, статус `passed`, 28 шагов. Копия результата и журналов команд сохранена в `artifacts/wsl-acceptance-20261017/` (файл `linux-result.json`). Тестовые хосты и сервер репозитория завершены. Подготовленная WSL-среда сохранена для повторных запусков.

Дополнительно на Linux прошли 16 тестов определения платформы и проверки архитектур: корректный Linux ReadyToRun, отказ для Windows, неправильной сигнатуры, ARM64 и 32-битного образа, нормализация RID без расширения списка поддерживаемых ABI. На Windows прошли 43 теста ядра и плагинов. Полный пакетный набор завершился с 140 успешными проверками из 142: две ошибки относились к размещению искусственного PE-заголовка в новых тестах, за пределами виртуального размера секции. Исправлена только тестовая заготовка; повторно прошли все 5 проверок архитектуры на Windows и весь выбранный набор из 16 проверок на Linux. Таким образом, все 142 пакетные проверки покрыты успешными запусками; полный набор после правки тестовой заготовки повторно не запускался. Журналы: `windows-tests.log`, `windows-architecture-tests.log`, `core-tests.log` и `linux-regression.log` в каталоге артефактов. Проверены также форматирование C#, синтаксис Python, отсутствие нулевых байтов в изменённых файлах и `git diff --check`.

WSL-прогон не является проверкой Docker или отдельной физической машины. Проверен вызов системной libc, но не доставка сторонней native-библиотеки из NuGet. Физические устройства, PostgreSQL, сетевые файловые системы и аварийное отключение питания остаются за границами этого сценария.

## Повторный запуск

Требуются Python 3.10+, .NET 10 SDK с ASP.NET Core runtime, доступ к NuGet.org и свободные локальные TCP-порты. Сценарий использует только стандартную библиотеку Python. Он собирает проекты в текущей копии исходников, создаёт тестовые пакеты и данные в новом каталоге, не удаляет существующие каталоги. Запускайте без python -O: проверки используют assert.

Windows, из корня репозитория:

```powershell
python tools/package-acceptance.py artifacts/acceptance-win-new
```

Для новой WSL-среды установите дистрибутив, .NET 10 SDK и Python, проверьте `dotnet --info`. В подготовленной Ubuntu-24.04 они уже установлены. Прогон должен запускаться Linux-интерпретатором и Linux-dotnet, а каталог результата должен лежать в файловой системе дистрибутива, не в /mnt/c или /mnt/d. Предпочтительна отдельная копия текущих исходников без Windows bin/obj и с изменениями этой приёмки.

Из корня Linux-копии репозитория:

```bash
python3 tools/package-acceptance.py "$HOME/thinkinghome-acceptance-linux"
```

Выберите новый путь для каждого запуска. При ошибке сценарий выводит имя журнала неуспешного шага. Только завершение с кодом 0 и result.json со статусом passed подтверждают прохождение всего сценария.
