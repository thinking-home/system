# Порядок реализации MVP менеджера плагинов

## Правило

MVP из [ADR-0002](ADR-0002-plugin-package-management-mvp.md) реализуется последовательно в семь этапов с соблюдением архитектуры [ADR-0001](ADR-0001-plugin-package-management.md). Проверки выполняются внутри каждого этапа; заключительный этап проверяет совместную работу компонентов.

| Этап | Содержание | Условие завершения |
|---|---|---|
| 1. Контракты и модель загрузки | Формат метаданных DLL, категории зависимостей, общий контракт, соответствие пакетов и сборок, целевые платформы; изолированный прототип DI, прямых ссылок, двух приватных версий и общих EF, атрибутов, делегатов | Модель загрузки подтверждена проверками; форматы и ограничения описаны |
| 2. Упаковка и статическая валидация | Согласованные метаданные DLL и nuspec, ресурсы и встроенные библиотеки, исключение пакетных зависимостей, чтение без исполнения кода, проверка утечек типов | Из проекта получается проверенный пакет; подготовлены корректные и ошибочные тестовые пакеты |
| 3. Источники и сервер | Минимальный NuGet V3 для папки, индексирование и проверка плагинов, клиент источников, разделение репозиториев, приоритеты, версии и скачивание | Клиент получает плагин с нашего сервера и библиотеку из NuGet без изменения установки |
| 4. Граф и план установки | Транзитивные зависимости, диапазоны версий, общие и приватные области, выбор runtime-ресурсов, повторная проверка контрактов, lock-файл и карта загрузки | Формируется проверенный план либо ошибка с цепочками требований; применение не требуется |
| 5. Установка и восстановление | Декларация корневых плагинов, дедупликация, хеши, временная область, согласованная фиксация, install со сменой версии, ci, validate, сериализация операций и удержание используемых файлов | Чистая установка воспроизводится; сбой сохраняет старое состояние |
| 6. Интеграция с хостом | Загрузчик, DI, генерируемый appsettings, проверка обработчиков, порядок жизненного цикла, применение после перезапуска; сначала группа реальных плагинов, затем расширение | Установленные пакеты запускаются без проектных ссылок хоста на них |
| 7. Удаление и приёмка | remove, обратные зависимости, пересчёт достижимости, сохранение настроек и используемых файлов; сквозные проверки платформ и инструкции | Выполнены критерии MVP ADR-0002 |

Первый этап выполняется одним проходом из трёх внутренних частей: описание контрактов, изолированный прототип, проверка сценариев и фиксация результата. Прототип не заменяет рабочий загрузчик и не означает готовность установки пакетов.

## Контекст

Основной технический риск — сохранение прямых типизированных ссылок между плагинами при изоляции приватных зависимостей. Текущие плагины обмениваются EF-типами, атрибутами и делегатами. Этот риск нужно проверить до построения механизма доставки.

## Обоснование

Проверенная модель загрузки задаёт требования к упаковке и карте зависимостей. Источники обеспечивают данные для разрешения графа. Проверенный граф позволяет реализовать согласованную установку, после чего подключается рабочий хост. Удаление использует уже существующий граф и механизм фиксации состояния.

## Последствия

На этапах 1–5 приложение сохраняет текущий рабочий загрузчик. Тестовый прототип отделён от продуктового кода. Неопределённости первого этапа фиксируются явно; обнаруженная несовместимость требует уточнения модели до следующих этапов.

## Как проверяется

У каждого этапа есть указанный в таблице результат и воспроизводимые проверки. Финальная приёмка не подменяет проверки отдельных этапов. Результат первого этапа хранится в [описании прототипа](../plugin-package-loading-prototype.md).
