# Границы MVP управления пакетами плагинов

## Правило

MVP позволяет установить скомпилированный плагин со всеми зависимостями, воспроизвести установку на другой машине с совместимой целевой средой и запустить систему после перезапуска. Конфликты объявленных зависимостей обнаруживаются до изменения рабочего состояния.

Решение уточняет очередность реализации [ADR-0001](ADR-0001-plugin-package-management.md), сохраняя его архитектурные правила. Отложенные проверки и возможности остаются частью целевой архитектуры, но не являются условием готовности MVP. Имена команд и файлов являются рабочими обозначениями. Реализация этим документом не выполняется.

### Обязательная функциональность MVP

| Функциональность | Минимальный объём |
|---|---|
| Формат пакета | `.nupkg`, манифест в метаданных DLL, согласованность с `.nuspec`, проверка признака плагина без выполнения кода |
| Упаковка | Общие правила сборки пакетов плагинов, включение ресурсов и явно объявленных встроенных библиотек |
| Источники | Отдельные списки репозиториев плагинов и библиотек с детерминированным приоритетом |
| Сервер репозитория | Выдача пакетов из локальной папки по минимальному профилю NuGet V3, проверка пакетов при индексировании |
| Разрешение зависимостей | Транзитивные зависимости, диапазоны версий, одна активная версия плагина, диагностика несовместимости с цепочками требований |
| Разделение библиотек | Платформенные, общие и приватные зависимости, разные версии приватных библиотек, одна согласованная общая версия контрактной библиотеки |
| Хранение | Одна копия каждой версии пакета на диске в пределах установки, встроенные библиотеки в каталоге плагина |
| Воспроизводимость | Декларация корневых плагинов и lock-файл с точными версиями, источниками, хешами и целевой средой |
| Установка | `install` с проверкой полного графа и сохранением прежнего состояния при ошибке |
| Изменение версии | `install <plugin>@<version>` с пересчётом графа и теми же проверками и гарантиями, что при установке |
| Восстановление | `restore --locked` / `ci` без пересчёта версий, с ошибкой при рассогласовании декларации, lock-файла или целевой среды |
| Удаление | `remove` с ошибкой, если плагин нужен другому, и исключением ненужных транзитивных зависимостей из графа после успешной операции |
| Валидация установки | `validate`: наличие и целостность файлов, совместимость, согласованность декларации, lock-файла, регистрации и карты загрузки |
| Загрузчик | Контексты приватных зависимостей, единые экземпляры плагинов и общих сборок, загрузка по подготовленной карте без сетевых обращений |
| Конфигурация | Автоматическая регистрация установленных плагинов и плагинов-зависимостей через генерируемый источник appsettings с сохранением пользовательских настроек |
| Жизненный цикл | Применение после перезапуска, порядок запуска по зависимостям, обратный порядок остановки, диагностика циклов |

Сохраняются гарантии согласованной фиксации состояния: работающий процесс использует прежний набор, его файлы не перезаписываются и не удаляются. Неудачная изменяющая операция не оставляет частично применённую установку. Отсутствие команды очистки не отменяет этих гарантий.

#### Проверка границ приватных зависимостей

В MVP обязательны:

- Статическая проверка типов публичного контракта, включая доступный потребителям public/protected API, вложенные DTO, обобщённые типы, базовые типы, интерфейсы, атрибуты и делегаты, как определено в ADR-0001.
- Проверка при упаковке и повторно при установке с фактически выбранными зависимостями.
- Проверка сигнатур и идентичности типов при регистрации обработчиков.
- Ошибка с указанием места утечки и зависимой сборки; автоматическое превращение приватной библиотеки в общую запрещено.

Передача объектов приватных библиотек через границу плагина запрещена уже в MVP, включая динамические каналы. Однако проверка содержимого `object`, `object[]`, коллекций и других динамических значений откладывается. В MVP для этих случаев действуют ответственность автора и интеграционные проверки; успешная статическая валидация не означает доказанного отсутствия динамических утечек.

#### Поддерживаемые платформы и пакеты

MVP корректно выбирает runtime-файлы для явно заявленных поддерживаемых платформ, включая native-библиотеки используемых плагинов и ресурсы локализации. Reference-сборки не используются для выполнения. Поддержка всех возможных NuGet-пакетов и ОС не требуется; список целевых сред должен быть определён при реализации.

Один lock-файл фиксирует решение для одной целевой среды. Пакеты должны содержать готовые runtime-ресурсы; необходимые результаты сборочных преобразований готовит автор плагина.

### Дополнительная функциональность после MVP

| Функциональность | Основание для переноса |
|---|---|
| Отдельная команда `update` | Версию можно изменить через `install <plugin>@<version>` с пересчётом графа |
| `prune` и автоматическая очистка диска | Неиспользуемые файлы пакетов могут оставаться на диске, не участвуя в загрузке |
| Проверка содержимого динамических значений | Обход `object[]`, DTO и коллекций требует протокола поддерживаемых данных, обработки циклов и ограничений; требования и пределы описаны в ADR-0001 |
| Анализатор с подсказками в IDE | Достаточно обязательной проверки при упаковке |
| Шаблоны конфигурационных секций | Достаточно регистрации плагина; настройки пользователь задаёт самостоятельно |
| Привязка пакетов и префиксов к источникам | На первом этапе достаточно заданного приоритета репозиториев |
| Поиск и просмотр каталога плагинов | Пакет устанавливается по известному ID |
| HTTP-публикация пакетов | Пакеты помещаются в папку сервера |
| Автоматическое отслеживание папки сервером | Достаточно явной переиндексации или перезапуска |
| Расширенная совместимость сервера с NuGet-клиентами | Сначала реализуется профиль, необходимый нашему менеджеру |
| Несколько целевых сред в одном lock-файле | MVP фиксирует одну целевую среду |
| Общий кеш между установками приложения | Достаточно дедупликации внутри одной установки |
| Независимые группы общих контрактов | MVP выбирает одну общую версию каждой контрактной библиотеки на приложение; приватная другая версия остаётся допустимой |
| История установок и команда отката | Сохранение прежнего состояния при неудачной операции обязательно уже в MVP; откат успешно завершённого обновления является отдельной возможностью |

### Возможности вне принятой очереди

Горячая замена плагинов, несколько активных версий одного плагина и обязательное выделение интерфейсов всех плагинов в отдельные пакеты не включаются в очередь последующих улучшений. Их введение потребует отдельного пересмотра архитектуры.

## Контекст

ADR-0001 фиксирует целевую архитектуру менеджера, загрузчика и репозитория, включая проверки границ приватных зависимостей. Для первой поставки необходимо отделить возможности, обеспечивающие корректную установку и запуск, от удобств эксплуатации и расширенных проверок.

## Обоснование

Разрешение зависимостей, изоляция загрузки, совместная идентичность контрактов и воспроизводимость составляют основную ценность механизма. Их перенос оставил бы нерешённой исходную задачу поставки независимо собранных плагинов.

Расширение репозитория, очистку, удобства обновления и разработчика можно реализовать после появления рабочего цикла установки. Статическая проверка обеспечивает раннее обнаружение ошибок контрактов; глубокий контроль динамических данных требует отдельной проработки и не блокирует первую поставку при явно обозначенных пределах проверки.

## Последствия

План реализации MVP должен покрыть весь обязательный цикл от упаковки и выдачи пакета до восстановления и запуска. Физически неиспользуемые пакеты могут накапливаться до появления очистки. Пользователь задаёт настройки вручную и знает ID устанавливаемого плагина.

В документации и диагностике MVP необходимо отличать подтверждённую корректность статического контракта от непроверенных динамических передач. Отложенная глубокая валидация не отменяет запрет утечек приватных объектов.

## Как проверяется

Готовность MVP проверяется сценариями ADR-0001, относящимися к обязательным возможностям, и следующими сквозными условиями:

1. Собранный плагин размещается в папке сервера, устанавливается по ID вместе с транзитивными зависимостями и запускается после перезапуска без проектных ссылок хоста на этот плагин.
2. Декларация и lock-файл воспроизводят установку в чистом окружении той же целевой платформы; новые версии не выбираются.
3. Конфликтующие приватные библиотеки работают изолированно, общие контракты сохраняют идентичность типов, несовместимые общие требования отклоняются.
4. Статическая утечка приватного типа и несовместимая сигнатура обработчика диагностируются до его использования.
5. Изменение версии через `install` применяет новый согласованный граф после перезапуска; неудачная операция сохраняет прежнее состояние.
6. Удаление используемого плагина отклоняется без изменений. Успешное удаление исключает ненужные транзитивные зависимости из графа и сохраняет пользовательские настройки; физическая очистка для готовности MVP не требуется.

Сценарии ADR-0001 для глубокого обхода динамических значений и команды очистки относятся к последующим этапам. Текущий документ фиксирует критерии будущей реализации и не является отчётом об их прохождении.
