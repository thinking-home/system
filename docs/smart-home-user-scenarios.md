# Умный дом: сценарии и договорённости

Дата фиксации: 14 октября 2026 года.

Последнее обновление: 31 октября 2026 года.

Статус: рабочие договорённости и идеи из обсуждения с пользователем. Это не утверждённая спецификация реализации и не согласованный состав первой версии. Реализация по этому обсуждению не начиналась.

## Как продолжать обсуждение

- Сначала разбираем пользовательские сценарии, затем обсуждаем экраны и технические решения.
- Задаём вопросы по одному.
- Ключевые идеи и решения необходимо подтвердить у пользователя перед реализацией.
- Основной интерес сейчас — сценарии для сенсорных устройств, но сохраняем также идеи автоматизации дома вне приложения.
- Сценарии описывают желаемое поведение конкретного дома и не должны быть жёстко зашиты в реализацию. Система должна предоставлять надёжную платформу автоматизации, например среду выполнения скриптов, которую пользователь настраивает под себя.

## Направление проектирования: универсальная платформа

**Уточнение границ задачи после изучения актуальной документации:** проектируем архитектуру и интерфейс клиентов — мобильного и стационарного. Серверная платформа плагинов, событий, скриптов и расписаний уже существует в `system`; нейтральная модель управления устройствами реализована в соседнем репозитории `D:\Source\device-model`. Не проектируем их заново. Упоминания платформы ниже следует понимать в контексте расширяемой клиентской основы и её интеграции с существующими серверными возможностями.

Опора для клиентов: `DeviceDescriptor → Endpoint → Capability / Property`, типизированные состояния и команды; `IDeviceHost` предоставляет discovery, query, execute и поток Changed. Комната сейчас представлена строкой `DeviceDescriptor.Room`. В system уже есть HTTP API, SignalR и модульный веб-интерфейс. По прямому уточнению пользователя текущий веб-интерфейс не используем для touch-клиентов: нужен отдельный нативный интерфейс. Контракт новых клиентов и их расширений ещё требуется спроектировать.

Пользователь подтвердил, что ссылок на device-model в system пока нет. Предлагаемый им способ интеграции — небольшой плагин-обёртка: либо создаёт хост устройств внутри system, либо подключается к отдельному процессу. Выбор варианта пока не сделан; это точка интеграции существующих частей, а не задача повторного проектирования модели устройств. Часть документации device-model описывает целевую картину: учитывать `notes/status.md` и фактические контракты кода.

### Нативные клиенты и интерфейс, управляемый сервером

Нативный интерфейс для мобильного и стационарного клиентов — требование пользователя. Способ его реализации ещё обсуждается. Пользователь предложил рассмотреть Server-Driven UI, например [DivKit](https://divkit.tech/ru/); окончательного выбора DivKit нет.

Пользователь подтвердил разделение ответственности: сервер определяет содержимое экранов, клиент предоставляет нативные компоненты и механизмы их работы. Следующая тема обсуждения — серверное описание интерфейса и привязка его элементов к данным и командам плагинов. Конкретный формат описания, API регистрации и контракт привязок пока не согласованы.

### Согласованное размещение клиентского API и редактора

- API для мобильного и стационарного клиентов выносится в отдельный серверный плагин по аналогии с WebUi. Название нового плагина пока не выбрано.
- Другие серверные плагины могут регистрировать свои элементы интерфейса и операции, доступные пользователю, через контракт этого плагина.
- Конкретные экраны собирает пользователь через редактор в существующем WebUI.
- Метаданные пользовательского интерфейса хранятся в БД.
- WebUI используется для настройки, нативные клиенты — для повседневного использования настроенного интерфейса. Это не отменяет требование отдельного нативного интерфейса для touch-клиентов.

Дальше требуется определить структуру зарегистрированного элемента, его настраиваемых параметров, экземпляра на экране и привязок к данным/операциям. Конкретные схемы БД, формат разметки и C# API регистрации пока не утверждены. Предыдущее предложение ассистента о C# API и шаблонах остаётся предложением; пользователь подтвердил размещение ответственности, но не конкретный синтаксис API.

По предварительному изучению официальной документации DivKit предоставляет нативное отображение, шкалы, переменные для динамических значений, обработку пользовательских действий и встраивание собственных нативных элементов. Это кандидат на слой отображения. Само по себе описание интерфейса не реализует связь с device-model, звонки, доставку системных уведомлений или работу приложения в фоне.

Источники для дальнейшего обсуждения: [переменные](https://divkit.tech/docs/en/concepts/variables), [действия](https://divkit.tech/docs/en/concepts/interaction), [собственные элементы](https://divkit.tech/docs/en/concepts/divs/2/div-custom), [шкала](https://divkit.tech/docs/en/concepts/divs/2/div-slider).

Нужно разработать универсальную платформу с базовыми возможностями и расширением через плагины. Платформа вместе с плагинами должна позволять реализовать все обсуждённые правила и сценарии, не фиксируя их набор в реализации.

Следующий этап — найти общее в сценариях и определить, какие общие понятия и механизмы следует вынести в платформу, а какие возможности должны предоставлять плагины. Конкретные правила дома должны собираться и настраиваться на этой основе.

Далее обсуждаем структуры данных и структуру интерфейса. Предложенный ранее переход сразу к выбору возможностей первой версии заменён этим порядком по просьбе пользователя.

Предмет дальнейшего обсуждения, а не уже принятые решения:

- общие понятия, необходимые для описания состояний, управления и автоматизации в рассмотренных сценариях;
- границы ответственности платформы, плагинов и пользовательских правил;
- структуры данных и способы расширения модели плагинами;
- структура интерфейса, позволяющая работать с базовыми и добавляемыми возможностями;
- проверка предлагаемых общих механизмов на всех собранных сценариях, включая отложенные, в пределах уже известных требований.

Конкретные сущности, схемы хранения, API и контракты расширения пока не выбраны. Перед реализацией ключевые решения согласуются с пользователем.

## Пользователи и устройства

В доме постоянно живут несколько человек, также приезжают гости.

Настенными Android-панелями пользуются все находящиеся в доме. Телефон — альтернатива панели, когда подходить к ней неудобно. У настенной панели есть постоянный контекст её расположения.

На телефоне и панелях нужен единообразный интерфейс с выбором любой комнаты. Панель по умолчанию показывает комнату, в которой установлена.

Приложение должно поддерживать локальную работу с полной функциональностью и удалённый доступ через интернет. Точный состав возможностей удалённого режима пока не определён.

Обсуждение удалённого управления отложено: для пользователя вопрос прежде всего в том, какие возможности можно обеспечить дёшево. Вернуться к нему при оценке технических вариантов и стоимости, а не продолжать сейчас уточнение удалённых сценариев.

Пожелание: высокая скорость, отзывчивость и плавные анимации. Позднее пользователь уточнил: интерфейс должен быть нативным, текущий веб-интерфейс для touch-клиентов не использовать. Конкретный стек ещё не выбран; среди вариантов — Server-Driven UI с DivKit.

## Свет и присутствие

- Управлять светом в любой комнате с телефона или панели. Пример: выключить свет на кухне, находясь на другом этаже.
- Управление светом с дивана — тот же сценарий дистанционного управления, а не отдельная функция.
- Основное выключение света должно происходить автоматически после длительного отсутствия людей.
- Пока в комнате есть человек, автоматика свет не выключает, даже если он неподвижен.
- На панели достаточно простого ручного управления; сложные групповые действия пока не нужны.
- Отдельная идея автоматизации: включать служебный свет в коридоре, когда кто-то есть дома или в коридоре. Точное условие ещё предстоит выбрать.

## Проверка дома перед сном

Проверка происходит заранее, до ухода в спальню, а не уже из кровати.

С любой панели хочется сразу увидеть:

- где включён свет;
- в каких комнатах есть люди — без определения личности (пользователь обычно понимает, кто где может находиться);
- где открыты окна и дверные створки;
- какие двери не заперты;
- состояние ворот, упомянутое в первоначальном пожелании общего обзора.

Свет можно выключать выборочно, учитывая тех, кто ещё не спит. При этом основная надежда — на автоматическое выключение после отсутствия людей.

Умный замок хочется запирать из приложения. Открытые окна и дверные створки закрываются физически. Состояния «дверь закрыта» и «замок заперт» различаются.

Обзор всего дома достаточно вызывать кнопкой. Постоянное отображение допустимо, если получится сделать его удобным. Конкретное отображение ещё не выбрано.

## Климат

Основной сценарий: подойти к панели и изменить желаемую температуру в комнате.

- Видны фактическая и заданная температуры.
- С телефона и панели можно выбрать любую комнату; панель по умолчанию показывает свою.
- Заданная температура действует до следующего изменения человеком, расписанием или другой автоматикой. Отдельный срок ручного изменения не задавали.
- Ручное управление вентиляцией и влажностью может понадобиться, но редко; подробности отложены.

## Шторы

Хочется автоматического открытия на рассвете и закрытия на закате.

Ручное управление тоже нужно, когда требуется нестандартное положение. Взаимодействие ручного управления с автоматикой пока не уточняли.

Предварительно согласованное управление: две кнопки «Закрыть» и «Открыть», между ними шкала. Шкала показывает текущее положение штор и позволяет менять его касанием. Подробности взаимодействия пока не разбираем.

## Временное отключение автоматики

Пример: хочется поспать подольше в спальне и отменить открытие штор на ближайшее утро. В остальных комнатах шторы должны открываться как обычно.

Для выбранной комнаты нужны возможности:

- отменить ближайшее срабатывание, после чего автоматика продолжает работать как обычно без ручного восстановления;
- включить или выключить автоматизацию.

Это должно быть реализуемо общими средствами платформы и плагинов, а не специальным жёстко заданным правилом для штор.

По просьбе пользователя дальнейшая детализация остановлена. В частности, пока не определено, относится ли включение/выключение к отдельному правилу (например, только утреннему открытию) или к другой единице автоматизации. Вопрос об этом был задан, но решение не принималось.

## Погода

На панелях нужны текущая погода и прогноз на день.

Сценарий: перед выходом понять, какую одежду надеть и брать ли зонт.

## Голосовая связь

Сценарии: позвать детей к ужину или поговорить с человеком на другом этаже, не крича через весь дом и не подходя к нему.

- Звоним в конкретную комнату, а не конкретному человеку.
- Разговор начинается после принятия вызова.
- Пока звонки только по отдельности, в одну комнату.
- Телефон можно зарегистрировать как отдельную «комнату».

Идеи на будущее:

- громкая связь на несколько комнат;
- режим «Не беспокоить» для комнаты;
- определение комнаты конкретного человека;
- радионяня — пока без проработки, по явной просьбе пользователя.

### Предварительное исследование существующих решений

- Control4 близок к сценарию звонков между панелями и смартфонами с принятием: [описание](https://docs.control4.com/o/intercom-anywhere), [настройки автоответа и «Не беспокоить»](https://www.control4.com/help/c4/user/userguide/content/topics/intercom/settings.htm).
- Alexa Drop In использует автоматическое соединение при наличии разрешения и отличается от выбранного сценария с принятием: [описание Amazon](https://digprjsurvey.amazon.com/csad/help/node/201602230).
- HomePod Intercom передаёт голосовые сообщения с возможностью ответа, а не непрерывный разговор: [описание Apple](https://support.apple.com/en-nz/101606).
- Linphone/SIP рассмотрен как возможная основа обычных звонков между панелями и телефонами: [описание Linphone](https://www.linphone.org/en/linphone-softphone/). Привязку к комнатам и интеграцию пришлось бы проектировать отдельно.

Это предварительные ориентиры, техническое решение не выбрано.

- получать оповещения о выбранных событиях.

Подробную проработку видеонаблюдения отложили. Критерии событий пока не определены.

## Гостевой доступ

Гостям нужен самостоятельный вход и выход на время проживания, а не прежде всего приезд в отсутствие хозяина.

Без приложения рассматриваются временный код, регистрация биометрии или физический ключ. После отъезда доступ отключается.

Гость на машине может войти в дом по своему ключу или коду и открыть гараж кнопкой изнутри. Пока этого достаточно; отдельный способ открытия ворот снаружи без приложения не требуется.

Для гаражных ворот хочется:

- открытия кнопкой изнутри;
- закрытия по таймеру при отсутствии препятствий по датчику;
- оповещения, если ворота долго открыты и не могут закрыться.

Дополнительный вариант: гость устанавливает приложение, хозяин регистрирует его в системе и задаёт срок доступа. Гость может открывать гараж через домашний Wi-Fi при подъезде либо через интернет-шлюз.

Зарегистрированное приложение гостя получает полные возможности управления домом, как приложение хозяина или панель; ограничение только гаражом или гостевой комнатой не требуется.

Доступ:

- автоматически прекращается по истечении срока;
- может быть отключён досрочно;
- может быть продлён.

Управление доступом не входит в функции приложения или панелей, в том числе приложения хозяина. Предположительно регистрацию приложений и сроки будут задавать вручную в конфигурации домашнего сервера. Механизмы управления кодами, биометрией и физическими ключами ещё не определены.

## Уведомления и история событий

Разобраны два примера настраиваемой автоматизации:

- Протечка → отправить команду перекрытия воды → уведомить о перекрытии.
- Дверь долго открыта → уведомить.

Для текущего обсуждения считаем, что отправленная команда перекрытия означает, что вода перекрыта. Проверку результата и обработку отказов отложили по просьбе пользователя. Это допущение обсуждаемого сценария, а не подтверждение надёжности физического оборудования.

Правила уведомлений:

- Получатели — все приложения с действующей регистрацией, включая гостевые, а также настенные панели. Это уточнение заменяет раннюю формулировку «все постоянные жильцы».
- Уведомления обрабатываются как обычные системные: учитывают звук, вибрацию и беззвучный режим устройства.
- Для протечки нужно привлечение внимания, включая звук, если он разрешён настройками. Если телефон настроен на вибрацию, используется вибрация; принудительного обхода настроек не требуется.
- Подтверждение прочтения и назначение ответственного не нужны: жильцы при необходимости связываются сами.
- Уведомления сохраняются в общей истории.
- После восстановления связи пропущенные события появляются в истории; системные уведомления о старых событиях не отправляются.
- Все зарегистрированные приложения видят всю историю, включая события до своей регистрации.

Архитектурная идея пользователя: отдельный плагин уведомлений. Детали реализации ещё не обсуждались. Условия отправки и цепочки действий должны оставаться настраиваемыми средствами автоматизации.

- готовая общая модель комнат, устройств и их состояний в изученном коде не была обнаружена.

Эти наблюдения предварительные: перед реализацией необходимо сверить актуальный код. Они не означают выбора веб-интерфейса или иной архитектуры для нового приложения.

## Точка остановки и продолжение

На 31 октября 2026 года пользователь попросил сначала сохранить все договорённости, затем перейти к обсуждению структур данных и структуры интерфейса универсальной платформы.

Последние уточнения: шкала штор показывает текущее положение и позволяет менять его касанием; для выбранной комнаты можно отменить ближайшее срабатывание автоматики, а также включать/выключать автоматизацию. Детализация этих действий отложена.

Последнее архитектурное решение: отдельный плагин API для нативных клиентов; другие плагины регистрируют элементы интерфейса и пользовательские операции; пользователь собирает экраны через WebUI, метаданные сохраняются в БД. Продолжить с модели элементов, их экземпляров и привязок.

Следующий шаг — спроектировать общую клиентскую основу и расширение её возможностей, опираясь на существующие system и device-model. Обсудить клиентские структуры данных, привязки элементов управления к существующей модели, структуру интерфейса и контракт расширений. Использовать сценарии как примеры для проверки, не превращая их в фиксированный набор встроенных правил. Серверные плагины, события и модель устройств заново не проектировать. Все архитектурные предложения сначала согласовать с пользователем.

Экраны, архитектура и состав первой версии окончательно не согласованы. Реализацию не начинать только на основании этих заметок. Продолжать обсуждение по одному вопросу.

Видеонаблюдение, радионяню, обработку отказов перекрытия воды и детали отключения автоматики не разворачивать без возвращения пользователя к этим темам. Удалённое управление отложено до оценки доступных недорогих технических вариантов.
